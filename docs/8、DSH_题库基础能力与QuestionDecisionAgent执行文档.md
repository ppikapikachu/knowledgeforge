# DSH 执行文档：题库基础能力与 QuestionDecisionAgent

> **执行对象：** DeepSeek Harness（DSH）  
> **目标：** 先为系统建立可筛选、可归属的题库基础能力，再实现能够根据用户选择的题库规划出题内容的 `QuestionDecisionAgent`。  
> **执行范围：** 仅后端 `backend/`。本阶段不开发题目生成 Agent，不修改前端，不实现用户端练题流程。

## 二、业务背景与术语边界

系统中需要区分两种不同用途的分类：**知识库**和**题库**，不要混为一个概念。

### 2.1 知识库 `knowledge_base`

知识库用于组织导入和沉淀的知识点，是知识来源的较大范围，例如：

- Java
- Android
- 数据库
- 分布式系统
- C/C++
- 未分类

知识点和知识导入任务目前已经使用 `knowledge_base_id` 关联知识库。保留现有模型及其语义，不要将 `knowledge_base` 改造成题库，也不要因为增加题库而破坏现有数据回填逻辑。

### 2.2 题库 `question_bank`

题库用于组织用户练习时可选择的题目范围，分类可以比知识库更细，例如：

- Java 基础
- Java 集合框架
- Java 并发编程
- JVM
- 原生 Android
- 数据库基础
- 分布式系统
- 未分类题库

一个知识库中的知识点可以服务于多个不同题库。例如，Java 知识库中的知识点可分别用于“Java 基础”“Java 并发编程”和“JVM”题库。因此：

- `knowledge_base` 代表知识的来源或粗粒度领域。
- `question_bank` 代表练题时用户选择的题目范围。
- 两者不要求一一对应，不能简单地把每个知识库自动等同于一个题库。

### 2.3 题目归属原则

本阶段采用 **每道题有一个主要题库归属** 的 MVP 方案：`question.question_bank_id` 指向主要题库。每道题仍然可以通过现有 `question_knowledge` 等关系关联一个或多个知识点。

不要在本阶段擅自实现“一道题同时归属于多个题库”的多对多关系。如果检查现有模型后发现已有等价能力，应优先复用，并在实施报告中解释最终采用的模型。

## 三、总体实施顺序

请严格按下列阶段推进，第一阶段通过后再实现第二阶段。

### 阶段 A：题库基础能力

1. 检查当前题目模型与现有 CRUD 查询。
2. 新增 `question_bank` 模型与 Alembic 迁移。
3. 给现有 `question` 增加题库归属字段，并安全处理存量题目。
4. 补充题库的查询、创建、编辑等基础接口，具体操作按现有权限与 CRUD 规范实现。
5. 在题目创建、编辑、查询、列表筛选和序列化中支持题库归属。
6. 提供初始题库数据（可重复执行，不重复插入）。
7. 完成迁移、接口和回归测试。

### 阶段 B：按题库范围决策的 `QuestionDecisionAgent`

1. 接收用户选择的一个或多个题库及出题要求。
2. 校验题库是否存在、是否启用，并解析所选题库的描述及范围约束。
3. 为所选题库检索可用知识点候选集，不能直接把所有知识点无差别交给 LLM。
4. 结合用户的题型、难度和题量要求，生成结构化的出题计划。
5. 计划中的每个分配项都必须明确目标 `question_bank_id`，并且知识点必须来自该题库检索到的候选集。
6. 对模型输出进行结构校验、候选知识点校验、题量校验和错误处理。
7. 测试计划生成逻辑。不在本阶段生成、保存具体题目。

阶段 A 和阶段 B 都完成且测试通过后，本任务结束。不要继续扩展到 `QuestionGenerateAgent`。

## 四、阶段 A 详细需求：题库基础能力

### 4.1 先做代码盘点

实施前确认并记录：

- `question`、`knowledge`、`knowledge_base`、`question_knowledge` 等模型及其现有关系。
- 题目创建、修改、详情、列表及分页的路由、Schema、Service。
- 当前题目类型、难度、状态字段采用的具体枚举或存储格式。
- 统一响应格式、异常处理和鉴权方式。
- Alembic 当前版本和迁移约定。
- 当前测试框架、数据库测试配置和测试命令。

根据代码盘点结果修改，不要重复创建已有能力。

### 4.2 建议的题库字段

以现有项目风格为准，至少应表达以下信息：

| 字段语义 | 要求 |
|---|---|
| 主键 ID | 沿用项目已有主键类型与命名风格 |
| 名称 `name` | 必填，去除首尾空白；按项目需求防止重复命名 |
| 唯一标识 `code`（若项目适合） | 用于稳定识别内置题库；唯一约束，避免依赖可修改的显示名称 |
| 描述 `description` | 说明该题库覆盖什么内容、哪些内容不属于本题库 |
| 启用状态 `is_active` 或现有等价字段 | 停用题库不可用于新决策和新建题目，但不能删除关联历史题目 |
| 创建/更新时间 | 遵循现有模型的审计字段规范 |

可根据项目已有 `Base`、时间字段和软删除规范复用，不要为相同用途重复造字段。题库名称的唯一性策略要和项目已有数据库及业务约定一致；若使用 `code` 作为唯一键，应保留合理的同名校验反馈。

### 4.3 初始化内置题库

为后续开发准备一组合理的初始题库。推荐至少包含：

| code 建议值 | 显示名称 | 内容边界说明 |
|---|---|---|
| `java_basic` | Java 基础 | 语法、面向对象、常用基础 API、异常处理等；不以 JVM 内存模型或复杂并发为主要考点 |
| `java_collection` | Java 集合框架 | List、Set、Map、集合实现与使用场景、迭代器等 |
| `java_concurrency` | Java 并发编程 | 线程、锁、并发工具、线程池、JMM 与并发安全等；对于 JVM 核心机制，可按项目题库边界决定是否排除或允许交叉考查 |
| `jvm` | JVM | 运行时数据区、类加载、垃圾回收、字节码与 JVM 性能排查等 |
| `android_native` | 原生 Android | Android 四大组件、生命周期、Handler/Looper、进程与线程、Framework 和原生应用开发等 |
| `database_basic` | 数据库基础 | SQL、索引、事务、基础数据库原理等 |
| `distributed_system` | 分布式系统 | 分布式一致性、服务治理、缓存与消息、常见分布式问题等 |
| `uncategorized` | 未分类题库 | 无法可靠分类或尚未完成分类的存量题目兜底 |

这些仅是 MVP 默认数据，不代表题库必须固定为以上列表。后续管理员应能维护题库。初始化必须可重复运行：已有同 `code` 的记录时应更新必要的默认描述或跳过，绝不能反复插入重复数据，也不能覆盖管理员后来修改的配置而不加区分。请结合项目现有 seed/初始化方式实现并测试。

### 4.4 存量题目迁移

- 为 `question` 增加题库归属字段，优先采用项目支持的外键约束。
- 迁移必须保证当前已有题目在迁移后仍可查询。
- 若题库归属字段要求非空，应先创建或确认“未分类题库”，再为存量题目回填，最后再设置非空约束；不要直接给非空字段加一个无法适配存量数据的迁移。
- 不要根据题目文字通过一次不可验证的批量猜测，将历史题目自动分到 Java、JVM 等细分题库。存量题目默认归入“未分类题库”，后续再由可靠的分类流程处理。
- `question_knowledge` 以及题目现有知识点关联必须保留。
- 外键删除策略不能导致删除题库时级联删除历史题目。应优先禁止删除仍被题目引用的题库，或遵循项目现有软删除方案。

### 4.5 题库接口

先检查项目当前 API 约定，再决定最终路由。若没有已有等价接口，建议具备以下能力：

- `GET /api/v1/question-banks`：分页或列表查询题库，支持按名称搜索、按启用状态过滤；返回题库基本信息以及必要的题目数量（若统计成本可控）。
- `GET /api/v1/question-banks/{id}`：查询题库详情。
- `POST /api/v1/question-banks`：创建题库。
- `PATCH` 或 `PUT /api/v1/question-banks/{id}`：修改名称、描述、启用状态等允许编辑的字段。
- 如项目对删除有统一约定，可提供删除接口；删除前必须检查是否仍被题目引用。对于内置题库和被引用的题库，不可进行会破坏历史数据的硬删除。

接口要求：

1. 使用现有 API 版本、响应体、鉴权、分页、错误码规范。
2. 创建或编辑时验证必填字段、名称/code 冲突、字符串长度和状态值。
3. 未找到题库应返回项目约定的明确错误，而不是 500。
4. 停用题库的处理规则一致：不再允许它作为新建题目目标或 Agent 决策目标，但历史题目仍可在列表和详情中显示，并可按业务规则进行历史查询。
5. 不要为了这次任务额外引入新的鉴权系统。

### 4.6 题目 API 的兼容和扩展

扩展现有题目 API，而不是另造一套题目 CRUD：

- 题目创建及更新支持设置 `question_bank_id`。
- 新建题目时校验目标题库存在并处于启用状态。对未显式传入题库的处理方式，应遵循兼容现有调用的最稳妥方案；若回退到“未分类题库”，需在接口文档和测试里明确。
- 题目详情与列表响应中提供题库 ID 和适当的展示信息，遵循已有的嵌套/平铺风格。
- 题目列表支持按单个题库 ID 筛选；如果现有筛选参数组织方式合适，可按一致风格扩展为支持多个题库。多选过滤语义必须是 **并集**：结果属于所选题库中的任意一个，而不是同时属于全部题库。
- 不得破坏原有关键词、题型、难度、状态、分页和排序筛选。
- 题库统计数应基于真实数据计算，不能伪造或在多个查询中重复计数。

### 4.7 阶段 A 验收标准

- 新增 `question_bank` 模型和向前兼容的 Alembic 迁移。
- 内置题库初始化可重复运行且不会生成重复记录。

- 原有题目与知识点关联未受破坏。
- 有对应自动化测试，测试能够覆盖正常情况及非法题库 ID、停用题库、重复标识、存量题目回填等边界。
- 数据库升级命令、降级风险和实际测试结果在交付报告中说明。

## 五、阶段 B 详细需求：QuestionDecisionAgent

### 5.1 Agent 的职责边界

`QuestionDecisionAgent` 的职责是把用户的练题要求转化成**可验证、可执行的出题计划**，不是生成题目正文。

它应当决定：

- 在用户选择的题库范围内，优先覆盖哪些知识点；
- 每个题库分配多少道题；
- 每个知识点分配多少道题；
- 各分配项的题型和难度分布；
- 哪些知识点暂时无法覆盖，以及原因。

它不负责：

- 生成题目正文、选项、正确答案或解析；
- 直接写入正式 `question` 数据；
- 擅自扩展用户选定题库范围；
- 把未检索到、未提供给它的知识点 ID 编造成有效知识点；
- 越过现有知识导入或题目管理流程。

### 5.2 输入要求

结合当前项目 Pydantic Schema 风格实现输入 Schema。以下是业务字段示例，应按现有命名规范落地：

```json
{
  "question_bank_ids": [1, 4],
  "total_question_count": 20,
  "question_types": ["single_choice", "multiple_choice", "short_answer"],
  "difficulty_distribution": {
    "easy": 40,
    "medium": 40,
    "hard": 20
  }
}
```

至少支持以下语义：

- `question_bank_ids`：用户选择的一个或多个题库 ID，必填且不能是空数组；ID 必须存在、启用且不重复。
- `total_question_count`：本次计划题量，必须是合理正整数；最大值由项目现有业务限制决定并写入校验。
- `question_types`：允许的题型集合，至少从项目现有支持的题型中选择；不能发明与系统题目模型不兼容的类型。
- `difficulty_distribution`：难度分配比例或计数，必须明确采用哪种表示方式；若采用百分比，需校验合法区间和总和，并将比例换算成整数题量。若项目已有难度策略，优先复用。
- 可选扩展项：用户希望重点复习的知识点、排除的主题、错题优先级等。仅在现有业务已经支持或本次实现成本合理时加入，不能把非必需扩展变成实现阻塞。

接口如果收到错误的题库 ID、停用题库、非法题型、非法题量或无效难度比例，应返回可理解的校验错误，不能默默忽略用户选择。

### 5.3 题库范围如何约束知识点

这是本 Agent 最重要的约束，必须优先保证范围正确，再优化计划质量。

每个题库需要能提供清晰的内容范围。优先使用以下信息构建候选集：

1. 题库自身的名称和描述，尤其是覆盖内容与排除内容。
2. 题库允许使用的一个或多个 `knowledge_base` 来源范围（只有在现有模型容易、安全地表达时才实现该映射；不能假定每个题库只对应一个知识库）。
3. 从已存在的知识点数据中检索与题库相关的候选知识点，沿用项目已有的向量检索封装；若已有向量服务不可用，需有可测试的降级策略，例如关键词/数据库查询。不要在本任务中引入付费服务或强制依赖 OpenAI。
4. 知识点候选需要包含稳定 ID、名称、必要的描述/内容摘要及必要的来源信息，便于 Agent 做选择。

示例边界：

- 用户只选“Java 基础”，候选应主要来自 Java 基础语法、面向对象、异常处理、常用 API 等内容，不能因为知识点来自 Java 知识库就把 JVM 垃圾回收作为默认重点。
- 用户只选“JVM”，应优先围绕类加载、运行时数据区、垃圾回收等 JVM 主题，而不是把所有 Java 语法题放进计划。
- 用户选“Java 基础 + 原生 Android”，计划可以同时分配这两个题库的题量，但每个计划项必须明确属于其中一个题库。**多选题库表示多个范围的并集，不会自动创建新题库，也不意味着一道题同时归属多个题库。**

如果当前数据模型没有显式维护题库与知识点的关系，不要假装已经存在可靠的一对一映射。MVP 可通过题库范围描述 + 候选检索 + LLM 在候选集内筛选来实现，并在结果校验中强制要求知识点 ID 必须来自候选集。

可评估未来增加 `question_bank_knowledge` 关联表来显式维护题库与知识点的可用范围，但除非当前需求无法可靠实现，不要在本阶段贸然增加不必要的复杂后台能力。若你判断必须新增该表才能满足可靠性要求，先在实现说明中解释理由，并采用最小方案，不要扩展前端。

### 5.4 计划分配规则

- 计划总题量必须与 `total_question_count` 一致。若因可用知识点不足无法实现，应明确报错或返回带有明确状态与缺口说明的计划，不能静默少题。
- 题库之间的题量分配应由可用候选知识点数量、用户选择的范围、用户显式的优先级以及题型/难度约束决定。
- 在没有用户指定题库权重时，允许使用可解释的默认分配策略；不得保证所有题库严格平均，除非项目现有产品规则明确要求平均。
- 不同知识点之间的分配应尽量避免重复覆盖同一细碎知识点，并照顾候选知识点的相关性与可用性。
- 同一知识点可规划不同题型/难度，但不应因复制计划项导致题量重复统计。
- 不允许通过把知识点强行改挂到其他题库来满足题量。
- 题目归属字段使用 `question_bank_id`；每一条计划分配项必须包含清晰的目标题库 ID。

### 5.5 推荐输出结构

请在项目现有 Schema 与 Agent 输出约定基础上实现结构化输出。推荐返回语义如下：

```json
{
  "total_question_count": 20,
  "planned_question_count": 20,
  "question_banks": [
    {
      "question_bank_id": 1,
      "question_bank_name": "Java 基础",
      "planned_count": 12,
      "knowledge_points": [
        {
          "knowledge_id": 101,
          "knowledge_name": "Java 面向对象",
          "planned_count": 4,
          "question_types": ["single_choice", "short_answer"],
          "difficulty_counts": {
            "easy": 2,
            "medium": 1,
            "hard": 1
          }
        }
      ]
    },
    {
      "question_bank_id": 4,
      "question_bank_name": "原生 Android",
      "planned_count": 8,
      "knowledge_points": []
    }
  ],
  "warnings": []
}
```

上述内容只是结构示例，不代表必须逐字采用。如果现有项目使用更合理的 Agent Plan Schema，可继续沿用，但必须保证：

- 可确定总题量与每个分配项题量；
- 每个分配项有 `question_bank_id`；
- 每个分配项引用真实存在且位于候选集中的知识点 ID；
- 能表达题型和难度分布；
- 可以说明候选不足、未分配题量或其他约束问题；
- 能被后续 `QuestionGenerateAgent` 直接消费，而无需重新猜测题目属于哪个题库。

### 5.6 LLM 调用与可靠性

- 通过项目已有 LLM 封装调用模型；遵守当前模型配置与请求参数规范。
- 优先使用 Pydantic 或项目已有结构化输出工具约束响应格式，不要单纯依赖 JSON 字符串提示后直接信任返回值。
- 校验题库 ID、知识点 ID、题型、难度和各级题量汇总。
- 模型输出无效时，使用项目现有重试规范进行有限重试；禁止无限重试。
- 如果模型响应依旧无效，应返回明确的领域错误/失败状态并留下可诊断日志，不得将无效计划当成成功。
- 不记录 API Key、敏感凭据或完整的秘密配置；日志只保留定位错误所需信息。
- 纯逻辑分配、Schema 校验、题量汇总等能力应尽可能拆成独立函数，方便不调用 LLM 的单元测试。
- 如果当前项目支持同步与异步模式，应遵守项目既有调用方式，不要在已有事件循环中错误地创建嵌套事件循环。

### 5.7 数据访问和候选查询

- 复用当前 `knowledge` 查询与向量检索能力。
- 过滤掉被删除、不可用或不应参与出题的知识点（具体条件以现有模型为准）。
- 如果知识点所属知识库已经记录，通过它限制来源范围；但不可错误地要求某个细分题库只能使用同名知识库。
- 候选不足时明确反馈；不要自动把其他无关领域的知识点混入候选集。
- 候选结果要稳定可追踪，便于排查某个计划为何选择该知识点。
- 不要为了实现此功能再复制一份知识点主数据表。

### 5.8 接口集成

如果项目已有 Agent/出题规划入口，应扩展现有入口。没有合适入口时，可以新增清晰的版本化 API，例如：

`POST /api/v1/question-plans/decision`

此路由名称只是建议，以当前项目 API 规范为准。它应接收用户的题库选择与出题要求，返回结构化计划，不保存具体题目。

要求：

- 请求和响应必须有正式 Schema。
- 校验与业务错误遵循项目统一响应规范。
- 需要沿用当前管理端/用户端鉴权边界；不要把管理员专用接口无条件暴露给普通用户，也不要新增绕过鉴权的测试入口。
- 不要把模型原始思维链或内部推理过程返回给客户端。只返回计划、必要的简短说明与警告。
- 不得在该 API 中直接调用题目生成流程或批量写入 `question` 表。

### 5.9 阶段 B 验收标准

- `QuestionDecisionAgent` 接受一个或多个启用题库 ID。
- 单题库和多题库均有测试，多题库语义为题库范围并集。
- 计划每一项都携带正确的 `question_bank_id`。
- 所有被计划的知识点 ID 都来自该题库的已检索候选集。
- Java 基础、JVM、Android 的边界有独立测试，至少验证不能仅因为都来自 Java/技术领域就互相混入全部候选。
- 非法/停用/不存在题库 ID、候选为空、候选不足、非法模型输出和题量无法满足时有明确处理。
- 题量汇总、难度分配、题型校验有不依赖真实 LLM 的单元测试。
- Agent 只生成计划，没有创建或修改正式题目数据。
- API 的请求/响应契约和典型调用方式有文档或测试覆盖。

## 七、建议测试清单

### 阶段 A：题库和题目接口

1. 空数据库可以执行迁移并初始化默认题库。
2. 重复执行初始化流程不会产生重复题库。
3. 已存在题目升级后不丢失，且被回填至未分类题库。
4. 可创建、查询、修改题库。
5. 重复 `code` 或其他不允许的重复标识会按约定失败。
6. 停用题库不能作为新题目创建目标，但关联历史题目仍能正常查询。
7. 创建、修改题目可正确保存并返回题库归属。
8. 题目列表按一个题库筛选正确；如果支持多选，验证是并集语义。
9. 原有题型、难度、关键词、分页、排序和知识点关联测试通过。
10. 删除被引用题库时不会导致历史题目删除或失去有效关联。

### 阶段 B：QuestionDecisionAgent

1. 只选择 Java 基础时，所有计划分配项的题库都是 Java 基础。
2. 只选择 JVM 时，计划不应默认混入普通 Java 语法候选。
3. 选择 Java 基础 + 原生 Android 时，输出可以包含两个题库，但每项只归属于一个题库。
4. 任一题库 ID 不存在、已停用或重复时，按预期拒绝或规范化处理；不要静默扩大范围。
5. LLM 返回不存在的知识点 ID 时校验失败并按有限重试/错误处理机制返回。
6. LLM 返回未知题型、非法难度或错误题量时不能被当作成功计划。
7. `planned_question_count`、各题库数量、各知识点数量之和相互一致。
8. 候选数量不足时产生明确警告或失败，不得伪造知识点。
9. 使用 Mock/Fake LLM 可运行 Agent 单元测试，不依赖真实模型服务。
10. 调用决策接口不应新增正式题目记录。
