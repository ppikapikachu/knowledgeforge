## 2. P0：向量索引生命周期和启动就绪保护

### 2.1 当前已知问题

现有题目 VectorStore 基于进程内存中的 FAISS。独立执行 `build_question_embeddings.py --all` 后，脚本进程退出，索引不会自动出现在另一个 FastAPI 进程中。服务重启后也需要重新构建。

因此，不能把“曾经运行过构建脚本”视为当前 API 服务进程的索引已经就绪。

### 2.2 目标行为

FastAPI 服务启动时，通过应用自身的 lifespan/startup 生命周期，在**当前服务进程内**初始化题目向量索引：

1. 创建/获取独立的 question vector store，继续与 knowledge vector store 隔离；
2. 从 MySQL 查询需要参与去重的题目；
3. 只为去重阻断状态的题目建立/恢复向量索引，状态规则必须与当前 `sync_question_dedup_state` 保持一致，通常至少包含 `pending_review`、`published`；
4. 排除 `rejected`、`disabled` 等不应阻断新题的状态；
5. 使用当前配置的 Embedding 模型及版本构建向量；
6. 初始化完成后记录总题目数、成功数、失败数、耗时、模型名称和索引版本；
7. 初始化过程必须幂等，不得重复添加相同 `question_{id}` 向量；
8. 索引就绪后，才允许新生成任务进入语义去重执行阶段。

### 2.3 就绪状态

为题目去重服务提供明确的运行状态，至少区分：

- `initializing`：正在初始化；
- `ready`：向量索引和必需依赖可用；
- `degraded`：索引构建或同步出现问题，语义去重不可信；
- `disabled`：通过显式配置关闭去重（必须有明确配置及日志）。

不得将 `degraded` 当成空索引，也不得在索引未就绪时静默地只执行 Hash 后就继续批量出题。

### 2.4 索引不可用时的处理

默认安全策略：

- 新的 AI 生成任务不能在语义去重不可用时正常进入正式生成流程；
- 对 API 返回明确、可读的服务不可用/任务暂不可执行信息；
- 已经进入执行阶段的任务，如果发现索引失效，应按现有任务状态机制安全失败或暂停，不允许无提示地跳过语义去重；
- Hash 精确去重可继续用于防止完全相同数据，但不能作为语义去重的替代品；
- 索引恢复成功后，允许管理员重新发起任务或按现有可靠任务机制恢复。

如果项目已有更合适的任务等待状态，可以复用，但不能虚构状态后不更新前后端契约。

### 2.5 MySQL 与向量索引一致性

MySQL 是唯一事实源，向量索引是可重建的派生数据。

必须处理以下情况：

- MySQL 保存成功，向量写入失败；
- 题目编辑后向量更新失败；
- 题目驳回/下架后向量移除失败；
- 启动重建期间，新的题目仍有任务写入。

要求：

1. 向量同步失败必须记录明确日志及题目 ID；
2. 必须将索引状态标记为 `degraded` 或等价状态，不能继续假装完整；
3. 提供幂等修复方式，能够从 MySQL 重新构建缺失/过期向量；
4. 避免全量重建和实时写入互相覆盖；
5. API 服务自身必须能判断当前进程的索引是否完整，而不是依赖独立脚本进程的内存状态。

### 2.6 部署约束

在题目向量索引仍为进程内存态且没有跨进程同步机制时：

- 正式部署明确限制为单个 Uvicorn worker / 单个 API 进程；
- 多线程后台任务可以使用同一进程中的共享索引；
- 启动配置、部署文档或启动检查应明确阻止/警告多 worker 配置；
- 不得宣称当前方案已支持多进程语义去重一致性。

本次不要求迁移 Qdrant 等持久化向量库，但必须把未来多进程扩展限制记录清楚。

## 3. P0：修复语义重复并发漏判风险

### 3.1 当前风险

现有实现报告证明：10 个线程同时写入完全相同题目时，数据库只保存一条。这主要依靠相同指纹、模块级锁和唯一索引。

但是语义改写题目的 Hash 不同，数据库唯一索引无法拦截它们。模块级 `RLock` 只在当前 Python 进程内有效，也不能自动证明多进程安全。

报告中最终保存校验的严格语义门槛是 0.85，而普通同范围/跨范围候选进入复核的门槛分别为 0.65/0.75。必须确认两个并发任务的初始复核都在对方落库之前完成时，最终保存阶段是否可能让相似度处于 0.65～0.84 的语义重复题同时入库。

### 3.2 必须达到的行为

在当前明确支持的单进程部署模式下，两个并发任务即使生成了 Hash 不同、语义重复的题目，也不能仅因为初次检索发生在对方入库之前而同时通过保存。

最终保存保护不能只依赖：

- `content_hash` / `dedup_key` 唯一索引；
- 0.85 单一最终阈值；
- 初次 check_batch 结果；
- 仅在每个任务内部存在的 batch_context。

### 3.3 建议实现原则

请基于实际代码选择最小且可验证的方式，不要求机械照抄某一种锁方案：

1. 候选生成及常规召回可并行执行；
2. 对最终入库阶段建立明确的并发保护；
3. 最终保护必须针对刚刚成功保存、已经进入阻断状态的新题重新检查；
4. 最终复核必须保留同范围/跨范围判定规则，不能只按一个 0.85 值简单放过 0.65～0.84 的候选；
5. 如果最终阶段发现一个初次复核时尚不存在的新候选，不能直接忽略。可以重新执行必要复核，或将该新题标记为 uncertain/不入库并进入有限补生成；
6. LLM 网络调用不得长时间占用 MySQL 事务或数据库行锁；
7. 不允许在最终保护期间因更新 FAISS 失败而假装入库与索引都成功；
8. 保存成功后，应在其他生成任务进行下一次最终校验前，让当前进程的向量索引看到新题。

如果采用进程级锁，请说明锁的粒度和临界区；如果采用数据库锁/预留表，请说明事务边界、过期回收和异常释放规则。

### 3.4 并发专项测试（必须）

至少实现以下测试：

| 场景 | 输入 | 预期 |
|---|---|---|
| 完全相同题目并发 | 10 个线程，同一题干和选项 | 只能保存一条 |
| 同范围语义改写并发 | 两个线程，Hash 不同但同一知识点、同一考查点 | 不能同时保存为两道重复题 |
| 跨知识点高相似并发 | 两个线程，题库相同但知识点不同，综合分超过 0.75 | 按跨范围规则复核，不能绕过最终保护 |
| 跨题库高相似并发 | 两个线程，不同题库但内容高度相同 | 仍执行全局精确层及跨范围严格策略 |
| 并发不同题目 | 两个线程，考查角度明显不同 | 两道题都应保留 |
| LLM 判 distinct 后竞争 | 两个任务先完成初次复核，随后其中一个先落库 | 另一个必须对新增候选重新核验，不得盲目沿用过期结果 |

至少使用一组真实 Embedding 的语义改写样本，不得只用 Mock 固定返回相似度。

### 3.5 多进程边界

本次若不实现共享向量服务/持久化向量数据库/跨进程语义锁，就明确声明多进程不受支持并强制单进程部署。

数据库唯一索引仍然必须保留，用于跨进程精确 Hash 兜底，但不得将它描述为能够解决跨进程语义重复。

## 4. P0：修正题目文本标准化及精确指纹

### 4.1 当前风险

现有指纹 v1 会移除全部空白。该策略对一般中文题干有帮助，但可能破坏代码题或技术文本语义。

例如：

```java
System.out.println("a b");
```

与：

```java
System.out.println("ab");
```

字符串字面量内容不同。如果标准化将所有空白无差别删除，可能造成错误相同的指纹。

### 4.2 目标

精确指纹的首要目标是避免误杀真正不同的题目。允许少量近似文本进入后续关键词/向量层，不允许为了增加 Hash 命中率而破坏代码语义。

### 4.3 处理要求

检查并改进以下情况：

- 普通中文题干：合并无意义的连续空白，但保留必要词语边界；
- Markdown 代码块：保留代码内部空白及换行的语义；
- 引号和字符串字面量：保留引号内部原始字符及空白；
- 技术标识符：保留大小写，例如 `HashMap`、`hashmap`；
- 运算符：保留区别，例如 `==` 与 `===`；
- 技术名称：保留 `C`、`C++`、`JDK 8` 等差异；
- Unicode 全半角：只处理确认不改变含义的等价形式；
- 选择题选项标签：可剥离 A/B/C/D 等展示标签，但必须保留选项正文和正确性关系；
- 选项顺序：继续保持既定的顺序无关签名策略，但需验证正确答案映射没有被破坏。

不要用一个无上下文的正则表达式删除题目所有空白。

### 4.4 指纹版本迁移

如果修改签名规则：

1. 新规则必须提升 `hash_version`，例如从 `1` 升到 `2`；
2. 先提供 dry-run 迁移报告；
3. 检查新规则可能产生的历史冲突组；
4. 不得自动删除任何历史题目；
5. 冲突处理沿用“报告给管理员人工裁决”的安全规则；
6. 重算脚本必须幂等；
7. 旧指纹和新指纹不得在同一规则下被错误比较。

如果通过测试证明不需要改变当前签名规则，也必须在报告中说明代码题风险为何已被现有实现覆盖，并提供测试证据。

### 4.5 必须新增的标准化测试

至少覆盖：

1. 普通中文仅空格/换行不同；
2. 代码块缩进不同但代码行为相同；
3. 字符串 `"a b"` 与 `"ab"` 不应精确 Hash 相同；
4. `HashMap` 与 `hashmap`；
5. `C` 与 `C++`；
6. `==` 与 `===`；
7. `JDK 8` 与 `JDK 18`；
8. 选项标签变化；
9. 选项顺序变化但答案对应关系不变；
10. 选项顺序变化但答案对应关系变化；
11. 单选和简答题型不同；
12. 代码块围栏与普通文本中的相似代码。

## 6. P1：uncertain 疑点的后台可追踪性

当前服务在 LLM 超时、非法 JSON 或无法确定时，会把该候选标记为 `uncertain`，保留新题并标记人工复核。这是避免误杀的合理策略。

但需要确认管理员是否有办法查看这些疑点。

本次后端至少检查并说明：

1. `question_dedup_record` 是否保存了候选题 ID、匹配题 ID、相似分数、范围类型、LLM 结论和原因；
2. `uncertain` 是否能通过题目 ID / 生成任务 ID 查询；
3. 当前题目详情或任务详情是否暴露必要的 `dedup_review_status` / 关联候选信息；
4. 如果现有 API 无法让后台读取，提供最小只读管理员查询 API 方案及 DTO，暂时不修改前端；
5. 不要把 uncertain 伪装成 duplicate，也不要因为 uncertain 阻止所有正常题目入库。

如果本项会明显扩大本次修复范围，可先输出 API 设计和所需字段，不必在本次强行完成 UI。

## 7. 阈值及校准规则

目前报告的初始配置：

- 同范围候选进入 LLM：`0.65`；
- 跨范围候选进入 LLM：`0.75`；
- 最终保存语义拦截门槛：`0.85`；
- 融合分：`0.6 * vector_score + 0.4 * text_score`。

本次默认保留，不允许为了让测试通过而随意降低阈值。

但必须检查最终保存校验与初次范围阈值之间的逻辑一致性，避免 0.65～0.84 的候选在并发竞争时被绕过。

12 组样本只能作为初始校准，不能宣称已充分证明阈值适用于所有题型。请保留 `calibrate_question_dedup_thresholds.py`，并说明后续扩充人工标注样本的执行方法。

建议后续积累至少 50～100 对带人工标签的样本，覆盖：

- 同题改写；
- 同知识点不同考查角度；
- 同题库不同知识点；
- 跨题库相同/近似题；
- 选择题与简答题；
- Java/Android/数据库/算法等不同技术领域。

本项样本扩充可以作为后续持续校准，不应阻塞当前 P0 修复。

## 8. 保留的既有业务规则

以下规则继续有效，不得在本次修复中被破坏：

1. 完全相同题目全局精确拦截，不调用 LLM；
2. 同题库且知识点相交，使用常规去重；
3. 不同题库，或同题库但知识点不相交，使用严格跨范围规则；
4. 跨范围低/中相似度不调用 LLM；只有达到跨范围高阈值才复核；
5. 同一主题不等于重复，同一知识点不同考查角度应允许保留；
6. `pending_review` 和 `published` 属于去重阻断状态；`rejected`、`disabled` 不应永久阻断新题；
7. uncertain 不直接判 duplicate；
8. 同批次、历史题和其他待审核题均需参与正确的候选检查；
9. LLM 只对 Top-K 少量候选批量复核，不进行全库逐条调用；
10. 维持有限次补生成及 `unfulfilled_count` 如实统计；
11. MySQL 是唯一事实源，向量索引可重建；
12. 保留现有 `question_dedup_record` 审计能力。
