# DSH：题目多层去重服务开发与 QuestionGenerateAgent 接入执行文档

> 版本：V1.0  
> 执行方：DSH（仅后端）  
> 目标：实现可复用的 `QuestionDeduplicationService`，接入现有 `QuestionGenerateAgent`，降低题目重复率，同时避免对全库逐题调用 LLM。  
> 开发边界：只修改 `backend/`；不修改 `frontend/`；不重做 QuestionDecisionAgent、KnowledgePointDemandService 和智能分配算法。

---

## 0. 本次必须遵守的核心业务规则

本次去重不是对所有历史题目使用相同阈值。必须按新题与候选旧题的题库、知识点关系，分成两种去重路线。

### 0.1 同范围：常规去重

新题和候选题同时满足以下条件，才属于“同范围”：

1. `question_bank_id` 相同；
2. 两道题的 `knowledge_ids` 至少有一个交集。

同范围题目走常规多层去重：精确 Hash、文本/关键词算法、向量召回、算法分数筛选、必要时由 LLM 复核。此范围可以采用相对宽一些的候选召回阈值，以减少漏掉语义重复题的概率，但仍然不能把“同知识点”直接当成“重复”。

### 0.2 跨范围：严格算法过滤

只要满足以下任一条件，就属于“跨范围”：

- `question_bank_id` 不同；或
- 两道题的 `knowledge_ids` 没有交集。

跨范围去重必须先通过严格的算法相似度门槛：

- 精确 Hash 命中：直接判定重复，不调用 LLM；
- 算法相似度未达到高阈值：直接判定不重复，不调用 LLM；
- 算法相似度达到高阈值：才允许进入 LLM 复核；
- LLM 只对少量高相似候选做最终语义判断，不允许逐条遍历数据库。

**不得因为题目属于不同题库或不同知识点，就完全不做去重；也不得因为向量分数一般相似，就跨范围调用 LLM。跨范围必须“严格算法过滤后，极少量候选才进入 LLM”。**

### 0.3 全局精确重复

标准化后的题目指纹 Hash 在全局范围检查，不受题库和知识点影响。完全相同的题目，无论属于哪个题库、知识点或任务，都直接拦截，不调用 LLM。

### 0.4 多知识点题目的范围判定

一题可能关联多个 `knowledge_id`。只有在题库相同且知识点集合至少有一个交集时，才视为同范围；否则按跨范围严格策略处理。

如果新题没有有效知识点关联，不能默认套用同范围宽松策略。应按跨范围严格策略执行，并记录缺少知识点关联的告警；如果现有业务规则要求每题必须关联知识点，则应在生成结果校验阶段直接拒绝无关联题目。

## 1. 开发前必须先检查现有项目

开始修改前，先阅读现有代码和模型，不得凭文档臆造项目结构。至少检查：

1. `Question` 模型、`question_knowledge` 关联模型，以及题目 `question_bank_id`、`content_hash`、`status` 等字段；
2. `QuestionGenerateAgent` 完整生成、校验、入库流程；
3. 现有 `QuestionRepository`、题目保存事务和任务统计逻辑；
4. 当前 Embedding 服务、向量数据库客户端、知识点向量集合、向量查询和 upsert 实现；
5. 现有 `question_generation_task.duplicate_count` 等统计字段；
6. 现有任务状态、待审核/已发布/已驳回/已下架状态约定；
7. 现有 MiMo/LLM 客户端封装、并发调用和超时处理方式；
8. 当前 Alembic head 和已有唯一索引。

### 1.1 技术复用原则

- 优先复用项目已经使用的 Embedding 模型、向量数据库、连接配置和客户端封装。
- 为题目建立独立的向量集合/collection 或独立 namespace，不能将题目向量和知识点向量混在同一逻辑集合中。
- 如果项目尚无可复用的向量服务，先输出技术差异和选型建议，不要直接引入一个新的向量数据库供应商，也不要悄悄换模型。
- 不得在每次任务开始时重新对整个题库计算 Embedding。
- 新题只计算一次向量；历史题目通过入库时同步建立索引，并提供一次性历史数据索引/补建命令。
- 保留现有 `content_hash` 兼容性；如需要更改标准化算法，必须设计版本字段和迁移/重算策略。

完成检查后，先输出简短的现状盘点，再实施开发；无需等待用户确认，按本文件继续完成。

## 2. 去重整体架构

实现独立服务，建议职责如下（目录、命名按现有项目风格调整）：

```text
QuestionGenerateAgent
    ├── 生成候选题目
    ├── 题目结构和业务校验
    ├── QuestionDeduplicationService.check_batch()
    │      ├── normalize_and_hash()
    │      ├── check_exact_hash()
    │      ├── retrieve_keyword_candidates()
    │      ├── retrieve_vector_candidates()
    │      ├── classify_scope()
    │      ├── calculate_algorithm_scores()
    │      ├── apply_scope_thresholds()
    │      └── llm_review_shortlist()  # 只处理阈值以上少量候选
    ├── 对重复候选有限次补生成
    ├── 最终入库前二次校验（并发安全）
    ├── 保存题目和向量索引
    └── 更新 task 的成功/重复/失败统计
```

服务应尽量保持纯业务职责，不要把完整去重逻辑写进 Agent Prompt 或 `QuestionGenerateAgent` 中。Agent 负责调用服务并处理返回结果。

### 2.1 去重处理的四层结构

1. 精确层：标准化文本 + Hash + 数据库唯一性保护；
2. 算法召回层：关键词/文本相似检索 + 向量 Top-K 检索；
3. 范围阈值层：按同范围/跨范围使用不同候选门槛；
4. 语义复核层：只对需要复核的少量候选批量调用 LLM。

算法检索的职责是“缩小候选范围”，不是单凭向量距离直接断言所有语义重复。

## 3. 题目标准化、Hash 和索引

### 3.1 标准化内容

实现稳定、可测试、可版本化的题目标准化函数。至少考虑：

- Unicode 规范化；
- 多余空格、换行、全半角标点等无语义差异清理；
- 题干和选项结构化处理；
- 选项标签 A/B/C/D 与选项内容分开；
- 保留代码符号、运算符、版本号、大小写敏感技术标识，例如 `C`/`C++`、`HashMap`、`JDK 8`、`==`、`===`；
- 不得粗暴删除所有标点或全部转小写，造成技术题含义丢失。

选择题选项可额外计算规范化选项签名，以识别仅调整选项顺序的相同题；不要把选项字母标签当作实际选项内容。判断题、简答题要按题型采用对应规范化方式。

### 3.2 Hash 规则

至少建立：

- `content_hash`：用于全局精确查重，包含标准化题干及必要的结构化题目内容；
- `hash_version` 或等效版本标记：防止以后升级标准化算法后新旧 Hash 无法解释。

不能仅使用题干 Hash 忽略选项，导致题干相同但考查不同的题目被误杀；也不能因为选项顺序变化就漏掉同一道选择题。具体签名构成需按题型实现并补测试。

### 3.3 数据库保护

- 在确认现有数据可迁移后，为适当的 Hash 字段添加唯一约束/唯一索引，或采用项目中等效的原子冲突保护机制。
- Hash 是全局保护，不因题库或知识点不同而放宽。
- 处理历史重复数据时先审计，不能直接删除线上数据。发现历史重复应输出迁移报告或清理建议。

## 4. 算法候选召回：禁止全库逐题对比

### 4.1 候选来源

候选题必须来自数据库及其题目向量索引：

1. MySQL：按题目状态、题库、知识点关系等条件过滤结构化数据；
2. 关键词/文本检索：利用现有全文索引或轻量检索机制召回文字相近题；
3. 向量数据库：对新题计算一次 Embedding，执行 Top-K 近邻检索。

合并候选时按 `question_id` 去重，并保留各召回通道分数。

### 4.2 向量内容

题目向量建议以“题型 + 题干 + 选项文本（如有）”构造。不要只向量化知识点名称；也不要把长篇解析作为主要向量内容，以免向量偏向解释文本而非实际考查的问题。

LLM 复核时则可以提供题干、题型、选项、标准答案、关联知识点名称等必要信息。

### 4.3 Top-K 与过滤

- Top-K 必须可配置并设置上限，建议初始从 10～20 个候选开始验证，不得无限扩大。
- 优先按状态过滤，默认纳入 `pending_review`、`published` 和当前批次已接受的候选题；`rejected`、`disabled` 默认不作为有效阻断候选，但须检查项目现有状态语义并在报告中说明。
- 题库和知识点元数据必须随候选返回，以判断所属范围。
- 搜索结果应包含题目 ID、题库 ID、知识点 ID 集合、题型、状态及算法分数。
- 向量库元数据过滤如果受限，可先取有限 Top-K，再由 MySQL 批量加载权威记录并完成范围分类；不能逐条 SQL/LLM 查询。

### 4.4 当前批次内部检索

同一生成批次的新题也必须相互去重。批次规模较小时，可在内存中计算两两文本/向量相似度；不要为几十道同批新题反复查询整个数据库。当前批次已经判定为重复的候选，不得再成为后续新题的“有效保留题”。

## 5. 两种范围策略：本次最重要的业务逻辑

### 5.1 范围分类

设新题为 N，候选旧题为 C：

```text
same_scope =
    N.question_bank_id == C.question_bank_id
    AND intersection(N.knowledge_ids, C.knowledge_ids) is not empty

若 same_scope 为 false，则为 cross_scope。
```

即：只有“同一题库 + 至少一个共同知识点”同时成立，才走常规策略。

### 5.2 同范围（同题库且共享知识点）：常规去重

- 全局 Hash 命中：直接重复；
- 算法召回使用常规候选阈值；
- 对中高相似候选可交给 LLM 做语义复核；
- 可采用比跨范围更宽的召回区间，降低同知识点内漏判；
- 仍需区分“同知识点不同考查角度”和“换一种说法问同一件事”。

例如：

- “HashMap 底层是什么数据结构？”
- “JDK 8 的 HashMap 底层采用什么数据结构？”

应识别为高度疑似重复。

但：

- “HashMap 为什么引入红黑树？”
- “HashMap 扩容机制是什么？”

不能仅因同属 HashMap 知识点就判为重复。

### 5.3 跨范围（题库不同或知识点不同）：严格去重

- 全局 Hash 命中：直接重复；
- 先经过关键词/向量/文本等算法严格过滤；
- 算法分数未达到“跨范围高阈值”：直接判为不重复，不调用 LLM；
- 只有算法分数达到跨范围高阈值的 Top 候选，才进入 LLM 复核；
- LLM 复核必须重点判断是否确实在考查同一个事实/能力，而非仅仅主题相关。

举例：不同题库或不同知识点都可能涉及 Java 集合，但不能因为共享“Java”“集合”等关键词就判重复。跨范围门槛应明显高于同范围的候选进入门槛。

### 5.4 阈值策略

不要将某个向量模型的 `0.8`、`0.9` 分数写死为通用标准。不同 Embedding 模型、距离度量和向量库分数方向可能不同。

请将至少以下参数做成后端配置（初期可通过配置文件/环境配置管理，是否暴露 Web 管理由后续阶段决定）：

- `same_scope_candidate_threshold`：同范围候选进入复核的起始阈值；
- `cross_scope_high_threshold`：跨范围进入 LLM 的严格高阈值，必须高于/严于同范围候选门槛；
- `vector_top_k`：向量候选上限；
- `keyword_top_k`：关键词候选上限；
- `llm_max_candidates_per_question`：单道新题最多送入 LLM 的候选数；
- `llm_batch_size`：一次 LLM 请求批量判断的候选数量；
- `max_regeneration_attempts`：重复题淘汰后的最大补生成次数；
- `max_total_generation_multiplier`：实际生成候选总量相对目标数量的上限。

阈值必须通过标注样本校准，输出误判/漏判情况。默认值应在实际 Embedding 模型上验证后确定，并在报告中注明依据，禁止无测试依据地宣称某个固定分值适用于所有数据。

## 6. LLM 复核规则

### 6.1 只对候选集调用

严禁：

- 让 LLM 从全题库逐题查重；
- 每道新题与每道历史题目各调用一次 LLM；
- 仅因知识点相同或题目主题相关就调用 LLM；
- 把整个题库题目列表塞入 Prompt。

必须先通过算法召回和范围阈值过滤，再选取极少量候选。候选对可批量提交 LLM，一次调用判断多个候选对，输出结构化 JSON。

### 6.2 判断结果

LLM 复核统一为：

- `duplicate`：实际考查目标、核心答案/推理基本相同，只是措辞变化；
- `distinct`：考查角度、条件、推理过程或答案实质不同；
- `uncertain`：证据不足、题目内容不完整或无法稳定判断。

复核输入包含：新题、候选题、题型、选项、答案、知识点名称，以及必要的评分说明。Prompt 要明确“同属一个大主题不代表重复”。

### 6.3 复核异常处理

- LLM 超时、限流、返回非法 JSON：不能把候选直接判为重复。
- 同样不能默默当作 `distinct` 并完全跳过审核。
- 将该判断记录为 `uncertain`，保留新题并标记需要人工审核，或按现有业务状态设置去重待确认标记；不得阻塞整个任务无限等待。
- 复核结果需要做 Schema 校验，非法结构有限次重试。

## 7. 去重结果与生成补充策略

### 7.1 单题结果

`QuestionDeduplicationService` 对每道新题返回结构化结果，至少包含：

```json
{
  "decision": "distinct",
  "scope_mode": "same_scope",
  "matched_question_id": null,
  "decision_method": "vector_and_llm",
  "algorithm_score": 0.0,
  "llm_reason": null,
  "needs_manual_review": false
}
```

字段可按现有项目 Schema 风格调整，但必须保留：最终决策、同范围/跨范围、匹配原题 ID、决策方式、算法分数、原因、是否需人工确认。

### 7.2 批次统计

生成任务要区分：

- 请求数量；
- 实际生成候选数量；
- 通过去重数量；
- 精确重复数量；
- 算法/语义重复数量；
- 不确定待人工核查数量；
- 普通生成失败数量；
- 最终入库数量；
- 因重试上限未补足数量。

兼容现有 `duplicate_count` 等字段，不随意改变已经被前端使用的字段语义。需要新增字段时同步更新后端 API 文档和任务详情响应，并保持旧字段兼容。

### 7.3 重复后补生成

如果任务目标 20 道，通过去重后只剩 16 道，可有限次补生成 4 道。

- 重试必须沿用原任务分配计划和题型/难度；
- 自动分配模式下补生成应遵守原知识点 allocated_count，不得擅自把题目转移到其他知识点；
- 单个知识点达到本次计划数量后，不得无限集中补该知识点；
- 受最大重试次数、候选生成总量倍数、模型调用预算限制；
- 仍不足时如实记录 `unfulfilled_count` 或项目等效字段，不得谎报成功。

## 8. 并发安全与向量索引一致性

向量检索不是数据库唯一约束，两个并发任务可能同时检索不到对方刚生成但尚未索引的题目。

必须设计最终入库保护：

1. 生成和 LLM 判断阶段不持有长时间数据库锁；
2. 最终入库前再次检查全局精确 Hash；
3. 使用数据库唯一约束/原子写保证完全相同题目不并发入库；
4. 对语义重复并发竞争设计短时串行化/锁策略，所有写入方都必须遵守；
5. 先明确 MySQL 与向量库的写入顺序、失败补偿和索引状态；
6. 不能出现题目已保存但永久没有向量、或向量存在但数据库题目不存在而影响后续查重的静默不一致。

可在项目已有事务/锁能力内实现短时去重写入锁；如果采用 outbox/索引待处理状态，需记录重试和修复机制。不要在调用 LLM 期间持有全局锁。

向量索引至少需要记录 `question_id`、`question_bank_id`、`knowledge_ids`、`question_type`、有效状态、`embedding_model/version`。向量库仅作召回，MySQL 中的题目和关联关系是最终事实来源。

## 9. 去重审计记录

现有任务可能只有 `duplicate_count`，不足以说明为什么被去重。检查现有模型后，建议新增 `question_dedup_record`（或项目已有等效审计表），保存每次判定。

至少记录：

- `id`、`task_id`；
- 新题标准化 Hash；
- 新题内容快照（注意长度/隐私和存储规范）；
- 新题题库 ID、知识点 ID 集合；
- 匹配的 `question_id`；
- 候选题库 ID、知识点 ID 集合；
- 同范围/跨范围标识；
- 关键词分数、向量分数、融合算法分数；
- 是否进入 LLM、LLM 决策及原因；
- 最终 decision、decision_method；
- Embedding 模型和版本；
- 创建时间。

对不重复题目不必保存所有全库候选，只保存进入最终判定的候选及汇总即可，避免日志量爆炸。

管理员前端本次不改造，但任务详情应保留未来查看重复明细所需的数据；本次至少保证任务 `duplicate_count` 等汇总准确。

## 10. 历史题目向量化与索引维护

必须提供可重跑、可断点续跑的历史题目向量索引构建命令：

- 仅索引符合查重状态范围的题目；
- 分批读取 MySQL，不一次性加载全库；
- 对已经有当前版本向量的题目跳过；
- 失败可记录并重试；
- 支持只补缺失向量；
- 支持统计总量、成功、失败、跳过数量；
- 记录 Embedding 模型版本，模型变更时可重建；
- 不得覆盖或删除业务题目。

还需要考虑向量索引巡检/重建：查询 DB 与 Vector Store 不一致的 ID 并修复。

---

## 11. 推荐服务接口（内部接口优先）

按项目现有代码风格设计，建议至少提供：

- `check_one(question, task_context, batch_context)`：单题查重；
- `check_batch(questions, task_context)`：批量查重，执行批次内部对比并协调检索；
- `index_question(question)`：题目通过保存流程后写入/更新向量索引；
- `remove_or_deactivate_index(question_id)`：下架/删除时同步标记索引状态；
- `rebuild_missing_vectors(batch_size, ...)`：历史题目补建索引；
- `get_dedup_stats(task_id)`：获取任务级去重统计。

优先作为内部 Service 使用，不要求新增公开 HTTP API。若现有管理员任务详情需要展示重复明细，只有在确有必要时才新增只读管理员 API，并同步 API 文档。

## 12. 测试验收要求

必须有单元测试、集成测试，以及至少一轮真实 Embedding/Vector Store 的冒烟测试。不得只 Mock 向量查询后宣称语义去重完成。

### 12.1 范围规则测试矩阵

| 新题/候选题关系 | 预期路线 | LLM 规则 |
|---|---|---|
| 同题库 + 共享知识点 | 常规去重 | 常规候选阈值后可复核 |
| 同题库 + 无共同知识点 | 跨范围严格去重 | 只有极高算法分数才复核 |
| 不同题库 + 共享知识点 | 跨范围严格去重 | 只有极高算法分数才复核 |
| 不同题库 + 无共同知识点 | 跨范围严格去重 | 只有极高算法分数才复核 |
| 任意范围，标准化 Hash 相同 | 全局精确拦截 | 不调用 LLM |

### 12.2 具体重复样例

至少覆盖：

1. 题干完全相同；
2. 题干空格/标点不同；
3. 选择题选项顺序不同；
4. 题干改写但答案和考查点相同；
5. 同一知识点但考查角度不同；
6. 不同知识点但主题词相同、实际考查不同；
7. 不同题库但内容几乎完全相同；
8. 不同题库且不同知识点但只有领域相关性；
9. 单选题和简答题问法相近但训练形式/答案目标不同；
10. 同一任务内部重复；
11. 两个并发任务同时生成相同/近似题；
12. LLM 复核超时/非法 JSON；
13. 向量库不可用、Embedding 失败和索引延迟；
14. `pending_review`、`published`、`rejected`、`disabled` 状态候选处理。

### 12.3 必须验证 LLM 调用门槛

通过 Mock/Spy 计数和真实日志确认：

- 全局 Hash 命中：LLM 调用次数为 0；
- 跨范围低/中相似度：LLM 调用次数为 0；
- 跨范围高相似度：才调用 LLM；
- 同范围相似候选：按常规阈值进入复核；
- 任何情况都不能对数据库全量题目逐个调用 LLM。

### 12.4 质量指标

建立一批人工标注的重复/非重复题目对，至少统计：

- 精确重复识别率；
- 语义重复召回率；
- 非重复题误杀率；
- 同范围与跨范围的 LLM 触发比例；
- 每道新题平均候选数；
- 每批题 LLM 调用次数和 Token/成本（若可获取）；
- 去重额外耗时；
- 向量索引成功率。

优先降低“不同考查角度被误杀”的风险。阈值必须通过样本验证后确定，不得只凭主观指定。

## 13. 兼容性与开发边界

- 只修改 `backend/`。
- 不修改 `frontend/`，不要求 Claude Code 配合改页面。
- 保留现有 `QuestionDecisionAgent` 计划结构和智能分配逻辑。
- 保留手动单知识点与 auto 多知识点两种出题模式。
- 保留当前任务状态和既有响应字段，新增字段必须向后兼容。
- 不将不同题库的题目自动移动到当前题库；去重只判断是否重复，不改题目归属。
- 不因为题目知识点不同就无条件放过重复题；按跨范围严格规则筛选。
- 不因为知识点相同就直接删除不同考查角度题目。
- 不随意引入新向量数据库/新 Embedding 服务；优先复用项目现有技术栈。
- 不在本次开发自动补题、题目统计后台、普通用户体系或 Flutter 用户端。

### 最终验收标准

必须同时满足：

- 同题库且共享知识点：常规去重正常工作；
- 不同题库或知识点不同：严格算法过滤生效，只有极高相似候选才进入 LLM；
- 全局精确 Hash 命中不调用 LLM；
- 无全库逐题 LLM 比较；
- 新题和历史题、同批题、并发任务均有去重保护；
- 题目入库及向量索引能可靠同步或可恢复；
- 重复计数、失败计数及最终成功数量准确；
- 旧出题模式、自动分配模式、题目审核发布流程均未回归。

**执行原则：先盘点现有实现，再基于当前项目的真实模型、向量服务和 Agent 接口实现；发现现有架构差异时采用最小改动适配，不得新建一套与原有知识点向量系统重复的基础设施。**
