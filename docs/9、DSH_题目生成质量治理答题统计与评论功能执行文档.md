# DSH 执行文档：题目生成、解析、质量治理、答题统计与评论

> **任务性质：** 后端功能开发与现有题库链路整合  
> **执行对象：** DeepSeek Harness（DSH）  
> **开发范围：** 仅修改 `backend/`；不得修改 `admin-web/`、Flutter 客户端或其他目录。  
> **前置条件：** `question_bank` 题库能力和 `QuestionDecisionAgent` 已完成并通过接口测试。  
> **核心目标：** 将“知识点分配计划”转化为可管理、可审核、可统计、可讨论的题目资产；组卷只读取已发布题目，不在组卷请求中调用 LLM。

## 0. 执行原则：先检查现状，不要盲目照文档造表

开始编码前，先检查项目现有代码、数据库模型、Alembic 迁移、认证体系、任务执行机制、答题/试卷相关模型和 API。输出一份简短的《现状核对清单》，再按本文档实现。

重点核对：

1. `question`、`question_option`、`question_knowledge`、`question_bank` 的实际字段和关系。
2. `QuestionDecisionAgent` 的真实输入、输出 Schema，不得臆造或复制一套不兼容的数据结构。
3. 项目是否已有普通用户表、普通用户认证、试卷/练习会话、答题记录、后台任务执行器。
4. `knowledge_import_task` 或其他后台任务目前如何持久化、执行、重试、恢复；优先复用成熟的任务执行机制，不要另起一套互相冲突的 Worker。
5. 当前数据库、SQLAlchemy、Pydantic、Alembic 版本，以及已有统一异常、权限、分页和响应格式。

**硬性约束：**

- 不要把 `admin_user` 当成普通答题用户表。答题记录和评论应关联项目真实的普通用户身份。
- 如果目前还没有普通用户身份体系，不得随便创建一个 `user_id` 字段却没有认证和数据归属方案。先在实施报告中指出缺口，并提出最小兼容方案；不要用管理员 ID、客户端任意传入的 user_id 或固定测试用户冒充真实用户身份。
- 不要重复创建项目已经存在的表或服务。字段命名和类型以现有项目约定为准。
- 数据库变更必须通过 Alembic，迁移可升级、可回滚（如数据迁移本身不能安全回滚，应说明原因）。禁止清空或重建现有业务表。
- 不引入 Redis、Celery、RabbitMQ 等新基础设施，除非现有架构确实无法满足，并先说明必要性。长任务不能只依赖进程内临时任务而没有持久化状态。
- 不改前端。本次只提供后端 API、Schema、服务、Agent、迁移和测试。

## 1. 产品方案与必须遵守的业务判断

### 1.1 生成时机

题目生成分为三个入口，分阶段实现：

1. **管理员主动生成（本次必须支持）**：管理员选择题库/知识点/题量/题型/难度，系统调用已完成的 `QuestionDecisionAgent` 生成计划，再调用 `QuestionGenerateAgent` 生成题目。
2. **知识点导入后的库存检查（本次不做自动批量出题）**：知识点成功入库后，未来由库存服务判断是否缺题；本次不要在文档导入链路里默认对每个知识点自动生成题目。
3. **自动补充（后续阶段）**：根据题目库存、使用量和时间策略触发生成任务，本次只为后续扩展保留合理边界，不实现定时自动补题。

**组卷接口不得调用任何 LLM，也不得同步等待题目生成或解析生成。** 组卷仅从已发布、可用的题目中检索；库存不足时返回明确的不足信息或可用数量，不得偷偷临时生成。

### 1.2 题目生命周期：生成成功不等于可以给用户练习

不要将 LLM 返回的题目直接视为合格题目。建议至少有以下题目状态（如项目已有状态机，应映射到现有命名）：

- `pending_review`：生成完成、程序校验通过，等待管理员审核。
- `published`：管理员审核通过，可用于组卷和练习。
- `disabled`：管理员下架，不再用于新组卷，但历史答题记录仍可查看。
- `rejected`：管理员判定不合格，保留原因和生成历史，不进入可用库存。

推荐默认行为：**AI 新生成题目先进入 `pending_review`，审核发布后才进入用户题库。** 后续如果题量很大，可以提供管理员显式开启的“程序校验通过后自动发布”策略，但不能默认把未经审核的 AI 内容直接面向用户。程序校验只能排除结构错误，不能证明技术事实一定正确。

这不是为了增加审批流程，而是控制 AI 幻觉、错误答案、错误选项和不严谨表述造成的长期题库污染。审核至少应支持单题审核、批量发布、驳回/下架和驳回原因。

### 1.3 解析生成：可选、异步、可人工覆盖

管理员创建题目生成任务时，可以选择 `generate_explanation`：

- `false`：只生成题目，不触发解析生成。
- `true`：题目持久化成功后，为合格题目安排独立解析生成任务。

解析生成不得阻塞题目生成的完成，也不得因为解析生成失败而回滚已保存的题目。管理员始终可以手动新增、编辑解析。

解析来源需要区分 AI 和管理员手动编辑。**手动编辑过的解析不能被后续自动任务覆盖。** 对已有手动解析再次请求 AI 生成时，默认跳过，除非管理员明确选择覆盖；覆盖操作需二次确认或使用明确参数。

解析生成的内容应简洁，优先解释：

- 正确答案为什么正确；
- 常见错误选项/错误判断为什么不正确（适用时）；
- 对应知识点的关键原理。

解析不是完整教材，不要生成冗长文章，也不能用解析代替题目答案字段。

### 1.4 综合准确率：定义口径，不要只存一个模糊百分比

成熟练习平台会在题目页展示提交/通过统计，并将题目内容、答案/解决方案、提交历史和讨论区分开展示。例如 LeetCode 官方帮助说明题目页展示 accepted submissions 与 total submissions，并提供 Description、Solution、Submissions、Discuss 等独立区域；Codewars 也把练习结果、社区解法和讨论分开组织。参考链接见本文末尾。

本项目不要直接照搬编码平台的指标定义，但应做到指标可解释、样本可见。建议题目统计提供：

1. **答题正确率（全部有效已判分答题次数口径）**：`正确的有效已判分提交次数 / 全部有效已判分提交次数`。
2. **首次作答正确率**：每个用户对该题第一次有效且已判分的提交，只计一次，正确人数 / 有首次判分记录的用户数。
3. **累计答题次数**：符合统计规则的有效提交次数。
4. **独立答题人数**：至少有一条有效提交的去重用户数。

统计规则：

- 只统计真实认证用户提交的、已完成判分的答题记录。
- 请求超时重试造成的同一提交不能重复入账，接口需要幂等。
- 被取消、未提交、无效请求、未判分和判分失败的记录不进入正确率分母。
- 单选、多选、判断等可确定判分的客观题可以自动判分。
- 简答题不能仅凭模型一次自由判断就混入客观题正确率。首期可以记录答案并标记 `ungraded` 或 `pending_review`，不计入正确率；后续如引入 AI 评分，必须有评分标准/评分结果/评分模型版本，并单独展示主观题评分统计，不能与客观题正确率混成一个百分比。
- 统计 UI/API 要返回样本数。样本量过小时显示“样本较少/暂不展示稳定正确率”，阈值通过配置管理（建议初始阈值 20，不能散落写死在多个业务代码中）。
- 不要把“独立答题人数”误称为“答题次数”，也不要只看用户数计算提交正确率。

初期从答题记录 SQL 聚合即可，不要为了一个百分比提前新增冗余统计表。后续数据量确实影响性能时，再评估汇总表/缓存，并保证可重算。

### 1.5 题目核心内容修改：保护历史答题数据

已发布题目且已经有人答题后，不能直接修改题干、选项、标准答案等核心内容，否则历史正确/错误统计将无法解释。

本次 MVP 采用简单、可控策略：

- 未被答题使用的待审核题目可以编辑核心内容。
- 已发布且已有答题记录的题目，允许编辑解析、标签等非判分核心信息。
- 如需修改题干、选项或正确答案，首期建议下架旧题并创建新题（新 question ID），旧题及其历史记录保留。不要对旧答题记录重新判分。
- 未来如果确实需要原位版本管理，再设计 `question_revision`，本次不要为了可能的需求提前实现复杂版本系统。

### 1.6 评论：属于题目讨论，不属于某一次答题

评论关联 `question_id`，不要关联某条 `question_answer_record`。同一道题的所有用户看到同一个讨论区。

首期建议实现：登录用户发表评论、分页查看评论、删除自己的评论、管理员隐藏/恢复评论。评论先做平面列表即可，不实现多层楼中楼、点赞、图片/附件、站内通知和复杂排序。数据库可预留扩展，但不要一次性实现一整套社区系统。

评论治理不能省略：有长度限制、频率限制、鉴权、软删除/隐藏状态、管理员处理能力。评论按纯文本存储；如支持 Markdown，展示端必须做安全过滤，禁止直接信任用户 HTML。不要在公开接口返回评论用户的敏感资料。

## 2. 后端总体流程

```text
管理员提交生成配置
        |
        v
创建 question_generation_task（持久化任务）
        |
        v
调用已完成的 QuestionDecisionAgent（或接收其已确认计划）
        |
        v
QuestionGenerateAgent 按 plan_item / knowledge_id / 题型生成
        |
        v
Schema 校验 + 业务规则校验
        |
        v
文本指纹去重 + 向量候选检索 + 必要时 LLM 语义复核
        |
        v
保存为 pending_review（逐题保存，支持部分成功）
        |
        +------ generate_explanation=false ------> 更新主任务状态
        |
        +------ generate_explanation=true -------> 创建/执行解析子任务
                                                   |
                                                   v
                                         写入 explanation（不覆盖 manual）
                                                   |
                                                   v
                                         更新解析状态和任务进度

管理员审核发布
        |
        v
published 题目进入可组卷库存
        |
        v
用户组卷只查 published 题目（不调用 LLM）
        |
        v
用户提交答案 -> question_answer_record
        |
        +--> 题目正确率/首次正确率/答题人数统计
        |
        +--> 答题结果页展示解析（若已生成）和 question_comment
```

## 3. 数据模型与迁移要求

以下为逻辑设计，不代表必须逐字照抄字段名。请根据现有 SQLAlchemy 模型命名风格和数据库版本调整；如果现有结构已有等价字段，应复用。

### 3.1 `question`：题目表增加必要字段

建议检查并补充：

| 字段 | 说明 |
|---|---|
| `status` | `pending_review/published/disabled/rejected`，如已有状态则做兼容映射 |
| `explanation` | 简易解析，TEXT，可空 |
| `explanation_status` | `not_requested/pending/processing/success/failed` |
| `explanation_source` | `ai/manual`，可空或按项目约定设置 |
| `explanation_updated_at` | 解析最近更新时间 |
| `content_hash` | 规范化题干/选项等生成的指纹，辅助精确去重；如另有去重表可复用 |
| `generation_task_id` | 来源生成任务 ID，可空，用于追溯；如已有关联表则复用 |

说明：题目状态、解析状态、解析来源是三种不同含义，不能合并成一个 status。`explanation_source=manual` 的记录受保护，不允许自动覆盖。

### 3.2 `question_generation_task`：生成任务

如果项目已有通用持久化任务机制，请按其模式增加题目生成任务，不要重复实现新的 Worker 框架。建议任务数据至少包括：

| 字段 | 说明 |
|---|---|
| `id` | 任务 ID |
| `created_by` | 发起管理员 ID |
| `question_bank_ids` 或计划快照 | 请求题库范围/计划快照，按实际结构存储 |
| `request_config` | 题型、题量、难度、是否生成解析等不可变请求快照 |
| `status` | `pending/running/partial_success/success/failed/cancelled` |
| `total_count` | 计划生成数量 |
| `success_count` | 通过校验并持久化的题目数量（未必已审核发布） |
| `duplicate_count` | 去重跳过数量 |
| `failed_count` | 失败数量 |
| `explanation_requested` | 是否请求生成解析 |
| `explanation_total/success/failed` | 解析子任务统计；若已有任务明细机制可放在明细表 |
| `error_summary` | 可读错误摘要，避免只存模型原始长响应 |
| `started_at/completed_at/created_at/updated_at` | 生命周期时间 |

应保留任务请求快照，防止管理员修改题库/知识点后，无法解释之前任务实际按什么配置执行。

每一道题的生成结果要有可追溯性。若项目已有 task item 表，记录每个计划项/知识点/题型的处理状态和错误；若没有，评估是否需要 `question_generation_task_item`。避免只保存一个总进度，失败时无法定位是哪一个知识点/题型失败。

### 3.3 `question_answer_record`：用户答题记录

如果已有答题记录表，优先扩展它；不要再建一张重复表。若没有，新增该表。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `user_id` | 普通用户 ID，来自认证上下文，不接受客户端任意指定 |
| `question_id` | 题目 ID |
| `paper_id` / `practice_session_id` | 所属试卷/练习会话，可空，按项目现状选择 |
| `user_answer` | 用户提交答案；可使用 JSON 存储选项 ID、判断值或文本，需和题型 Schema 一致 |
| `is_correct` | 是否正确，可空；未判分不能伪造 false |
| `score` | 得分，可空 |
| `grading_status` | `graded/ungraded/pending_review/failed` 等，按项目命名统一 |
| `time_spent_ms` | 答题耗时，可空 |
| `idempotency_key` | 提交幂等键，防止网络重试重复计数；需有合适唯一约束（按 user/session 范围设计） |
| `created_at` | 提交时间 |

必要索引：`question_id + created_at`、`user_id + question_id + created_at`、会话/试卷查询索引，以及幂等唯一索引。

答题记录要不可随意覆盖。一次成功提交形成一条记录；用户再次答题形成新记录。若用户修改未提交答案，不应写入答题记录。

客观题判分规则：

- 单选：选择的正确选项 ID 与标准答案一致。
- 多选：首期建议采用完全匹配规则（漏选或多选均判错）；如已有部分得分规则，沿用并明确统计口径，不要默默改变。
- 判断：布尔答案匹配标准答案。
- 简答：首期不纳入客观题正确率。可保存文本和未判分状态；人工评分或未来 AI 评分另行定义，不允许模型输出一个随意布尔值混进客观准确率。

如果题目核心内容可能发生变化，应遵循 1.5 的规则，保证历史记录仍指向内容稳定的旧题 ID。

### 3.4 `question_comment`：题目评论

如果已有评论/讨论模块，复用；否则新增。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 评论 ID |
| `question_id` | 题目 ID |
| `user_id` | 普通用户 ID |
| `content` | 评论纯文本，长度上限建议 1,000～2,000 字符，配置化或统一校验 |
| `status` | `visible/hidden/deleted` |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |
| `deleted_at` | 软删除时间，可空 |
| `moderated_by` / `moderated_at` / `moderation_reason` | 管理员处理信息，可按现有审计规范拆分 |

首期不做多层回复。评论 API 默认只返回 `visible` 评论，按创建时间倒序或产品确定的稳定排序分页。自己删除使用软删除；管理员隐藏评论要记录操作者和原因。

必要索引：`question_id + status + created_at`、`user_id + created_at`。

### 3.5 暂不新增的表

- 首期不新增 `question_statistics`：先用答题记录聚合，确认性能问题后再做可重算的统计快照。
- 首期不新增 `question_revision`：已使用题的核心内容修改按下架旧题、新建新 ID 处理。
- 首期不新增独立 `explanation` 表：解析数量和题目一对一，放在 `question`。
- 首期不新增 `question_pool` 表：库存判断是业务服务，先按 `question_bank + knowledge + published questions` 聚合计算；库存策略字段是否持久化属于下一阶段。

## 4. QuestionGenerateAgent 开发要求

### 4.1 输入

直接对接现有 `QuestionDecisionAgent` 输出，不得自创一套相互不兼容的计划 JSON。每个计划项至少要能确认：

- `question_bank_id`
- `knowledge_id`
- 计划题量
- 题型及各题型数量
- 难度分布

生成任务还要带 `generate_explanation`。注意它控制后续解析工作，不要求题目 Agent 同步生成解析。

### 4.2 知识上下文

根据 `knowledge_id` 从数据库获取知识点名称、正文、所属知识库、关联信息及必要上下文。不要只把知识点名称交给模型。模型引用的知识点和题库必须经过数据库校验，禁止模型自行编造 ID。

### 4.3 输出结构

使用 Pydantic/结构化输出校验，按实际题型定义 Schema。建议统一题目结构包含：

- 题型、难度、题干；
- 选择题选项（选项 ID/标识由后端生成，不依赖模型产生稳定数据库 ID）；
- 标准答案；
- 关联知识点；
- 简短的生成质量自检信息（内部记录，可不展示给用户）。

题目生成 Agent 不得随意改变计划的题库、知识点、题型和数量。实际生成数量可能因为去重/质量校验不足而少于计划值，必须在任务结果中如实展示。

### 4.4 校验

至少实现以下程序化校验：

- 题型和字段结构完整；
- 题干非空，长度合理；
- 单选题选项数符合规则，且恰好一个正确选项；
- 多选题至少有一个正确选项，答案选项必须存在；
- 判断题答案值合法；
- 简答题有参考答案；
- 题目关联的题库、知识点均真实存在且与计划一致；
- 不能保存空答案、空选项或重复选项；
- 难度值只能使用项目已定义枚举；
- 不允许在题干/选项/答案中泄漏系统提示词或出现明显占位内容。

程序校验不等于事实准确性。生成题目默认进入 `pending_review`，等待管理员确认。

### 4.5 去重策略

实现分层去重，避免对每道题都调用一次昂贵 LLM：

1. **规范化文本指纹**：对题干做空白、标点、大小写等合理标准化；结合题型和必要的选项信息生成 hash，识别完全相同/近乎完全相同的问题。不要过度规范化导致不同题目 hash 冲突。
2. **向量候选检索**：使用项目当前已有的 embedding 和向量数据库。优先检索同知识点/同题库，再扩展到全局相似候选；阈值配置化。不得新增 OpenAI 专属依赖或改变现有 embedding 服务提供方。
3. **语义复核**：只对相似度落入待判断区间的候选调用 LLM，判断考查目标、正确答案和实际解题要求是否重复。措辞不同但考点和答案实质相同应判为重复；考查角度不同且有独立学习价值可保留。
4. **落库前二次检查**：并发任务可能同时生成相同题目，保存前必须再次检查。通过事务、唯一指纹或任务幂等机制避免重复写入。

去重范围不应局限在当前知识点；全局精确重复应阻止。语义检索优先当前知识点与题库，再判断跨知识点重复。保存重复跳过原因和匹配到的已有题目 ID，便于管理员排查。

### 4.6 重试和部分成功

- 对结构化输出失败、可修复字段错误、生成数量不足可有限次数重试。
- 对确定重复的题目，不要原样重试无限循环；可要求模型更换考查角度后重试一次，仍重复则记为 duplicate。
- 每次重试次数、失败原因和模型错误要可追踪。
- 每个有效题目独立持久化，不能因批次中一题失败就丢弃整个批次。
- 任务终态要正确区分全成功、部分成功、全部失败和取消。
- 任务重启/重试不能把已经成功保存的题目重复插入。

## 5. 可选解析生成任务

### 5.1 触发条件

管理员创建生成任务时传入 `generate_explanation`。当题目成功保存后，若 `true` 且题目尚无手动解析，则创建解析工作项。解析任务和题目生成任务分开统计。

### 5.2 解析生成输入/输出

输入：题干、题型、选项、标准答案、关联知识点正文。  
输出：简洁、基于知识上下文的解析文本。

需要对输出做非空、长度上限、明显无关内容等校验。解析生成失败不改变题目状态，不删除题目，支持单题重新生成。

### 5.3 手动编辑保护

- 管理员创建/编辑解析后设置 `explanation_source=manual`。
- 自动任务开始前和写入前都检查来源，防止任务运行期间管理员手动编辑后被 AI 覆盖。
- 如果检测到已变成 manual，任务应标记 `skipped_manual_override` 或等价状态。
- 管理员明确要求重新 AI 生成时，先保留旧解析或要求确认覆盖；不得静默覆盖。

### 5.4 任务状态

解析状态与题目生成状态独立。主生成任务可以在题目已保存、解析仍处理中时报告“题目生成完成，解析生成中”；不要把两者混成一个模糊的 `running`。

## 6. 用户答题记录、判分和统计

### 6.1 提交 API 的基本要求

提供用户端答题提交 API（路由按项目当前 `/api/v1` 风格命名），至少支持：

- 当前登录用户身份从 Token/认证上下文取得，不接受请求体传 `user_id` 作为可信身份；
- 校验题目存在、已发布、可作答；
- 校验用户答案格式与题型匹配；
- 幂等键防止网络重试重复记账；
- 写入一条不可覆盖的答题记录；
- 客观题执行确定性判分，返回判分状态、是否正确和必要结果；
- 不要在答题接口把正确答案提前返回。提交成功之后的答题结果接口再返回答案与解析（按项目产品策略控制）。

如果项目暂时没有试卷表/练习会话表，`paper_id` 可空或先不加，不要为了填字段臆造一个不存在的外键。

### 6.2 统计 API

提供题目维度统计接口，或在题目详情响应中组合统计摘要。至少返回：

```json
{
  "graded_attempt_count": 120,
  "correct_attempt_count": 78,
  "attempt_accuracy": 0.65,
  "first_attempt_user_count": 90,
  "first_attempt_correct_count": 63,
  "first_attempt_accuracy": 0.70,
  "unique_user_count": 95,
  "is_sample_sufficient": true
}
```

以上仅为响应示例，实际字段使用项目命名规范。统计必须由数据库记录计算，不能依赖前端传入或 Agent 返回的统计值。

- `attempt_accuracy` 以全部有效且已判分提交记录为分母。
- `first_attempt_accuracy` 以每个用户对该题首次有效且已判分记录为口径。首次提交未判分时，待其进入判分状态后按统一规则纳入；同一用户后续记录不能替代首次记录。
- `unique_user_count` 按有效答题记录中的去重用户数统计。
- 需要明确统计时间范围；默认全量历史，同时可预留时间范围筛选。
- 样本不足时仍可返回次数，但前端应将准确率显示为样本不足/暂不展示；阈值从统一配置读取。

### 6.3 未来库存统计边界

本次的答题记录只代表用户实际提交了答案，不代表题目已被展示或加入试卷。未来如需按“曝光/展示次数”进行库存轮换，应新增题目展示/发放记录或基于练习会话的可靠事件，不能拿答题提交次数冒充展示次数。

## 7. 评论功能

### 7.1 API 能力

按现有接口风格提供：

- `GET`：获取指定题目的可见评论，分页；
- `POST`：当前登录用户发表评论；
- `DELETE`：用户删除自己的评论（软删除）；
- 管理员接口：分页查看评论、隐藏/恢复评论、记录处理原因。

评论关联 `question_id`，不要求必须先有一条答题记录。是否要求用户答过题才可以评论，首期建议不强制，但必须登录；如产品希望限制，可以通过配置控制，不要把评论绑在一次答题记录上。

### 7.2 安全和质量

- 评论长度上限、频率限制、重复内容限制；
- 纯文本存储与安全输出；
- 管理员隐藏评论后，用户接口不可见；
- 用户只能删除自己的评论；
- 管理员处理行为留审计信息；
- 默认按时间倒序分页，并保证稳定排序（`created_at + id`）；
- 评论接口不得返回邮箱、手机号、内部用户 ID 等敏感信息，只返回必要的公开昵称/头像（前提是项目允许公开这些资料）。

首期不开发点赞、收藏评论、多层回复、私信、通知、图片和附件。

## 8. 题目审核和管理员操作 API

后端需要提供足够支撑管理端的 API，但不得修改 `admin-web/`。

至少支持：

1. 查询生成任务列表、任务详情、进度、失败明细。
2. 创建题目生成任务，参数必须校验题库、知识点范围和数量。
3. 查询待审核题目列表，支持题库/知识点/题型/难度/生成任务筛选。
4. 查询单题详情（包含选项、知识点、解析状态、来源任务）。
5. 编辑待审核题目的题干/选项/答案/解析。
6. 发布、驳回、下架题目；已发布且有答题记录的核心内容修改按 1.5 处理。
7. 手动生成/重新生成单题解析；明确是否允许覆盖手动解析。
8. 管理评论：查看、隐藏、恢复。

所有管理员接口都要验证管理员身份和权限。普通用户不能发布、下架题目或修改官方解析。

接口命名遵循当前项目规范。不要在没有检查现有 API 的情况下机械照抄本文档路由。

## 9. 任务执行、并发和稳定性

- 题目生成和解析生成均属于可能持续较长时间的工作，应通过持久化任务状态跟踪。
- 优先复用现有任务执行框架；如果现有实现只支持知识导入，抽取可复用的任务运行能力，不要让题目任务和知识导入任务耦合在业务逻辑中。
- 不能只在 HTTP 请求里同步等待 LLM 全部生成。
- 不能仅依赖进程内 `BackgroundTasks` 作为唯一持久化保障；服务进程重启后任务要能恢复或标记失败并可重试。
- 多个 Worker/实例时使用数据库锁、原子状态更新或租约机制，确保一个任务不会被多个 Worker 同时执行。
- LLM 调用设置超时、有限重试和最大并发，避免批量任务打满模型额度。
- 任务取消要有明确语义：尚未处理项停止；已经保存的题目保留，不做隐式删除。
- 记录模型名、提示词版本、耗时、token/成本元信息（项目可获取时），但不得把密钥、完整敏感提示词或用户隐私写入日志。

## 11. 开发阶段与交付顺序

不要一次性并行开发所有功能。按下列阶段顺序实现，每阶段通过测试后再进入下一阶段。

### 阶段 A：题目生成和质量治理

- 实现 `QuestionGenerateAgent`，读取真实知识点内容并严格遵守 DecisionAgent 计划。
- 实现结构化输出、题型规则校验、分层去重、落库幂等、部分成功。
- 新题默认 `pending_review`，提供审核列表、发布、驳回/下架 API。
- 创建持久化题目生成任务 API，复用现有任务执行体系。

**阶段 A 验收：** 可以通过接口创建生成任务，任务可追踪；生成题目准确归属指定题库和知识点；重复题被拦截；审核前不出现在用户组卷可用库存；重启/重试不会重复插入。

### 阶段 B：可选解析生成

- 增加 `generate_explanation` 参数。
- 题目保存后异步安排解析任务。
- 解析状态、来源和失败重试可追踪。
- 手动解析不被自动任务覆盖。

**阶段 B 验收：** 不勾选时不产生解析任务；勾选时题目先完成保存，解析随后运行；解析失败不影响题目；管理员手动编辑后自动任务跳过。

### 阶段 C：答题记录和统计

- 复用或新增答题记录模型。
- 完成客观题服务端判分、幂等提交和历史记录。
- 完成全部提交正确率、首次作答正确率、答题人数、样本充分性统计。
- 简答题未评分记录不混入客观题准确率。

**阶段 C 验收：** 同一用户重复答同一道题会产生独立记录；网络重试不会产生重复记录；统计值可通过手工 SQL/测试数据复核；没有判分的记录不进入分母。

### 阶段 D：评论

- 完成评论列表、发表评论、删除本人评论、管理员隐藏/恢复。
- 完成分页、鉴权、软删除、频率/长度校验和审计。

**阶段 D 验收：** 不同用户访问同一道题看到同一个评论区；隐藏评论普通用户不可见；用户无法删除或修改他人的评论；HTML/XSS 内容不会被不安全执行。

### 阶段 E：整体联调和文档

- 确认组卷逻辑仅查 `published` 题目，不调用 LLM。
- 用户答题结果可返回官方答案和解析状态；评论独立分页加载。
- 为所有新接口补充 OpenAPI/接口文档、请求/响应样例、权限说明。
- 输出数据库迁移说明、测试报告、已知限制和后续事项。

## 12. 必须覆盖的测试用例

### 12.1 题目生成

- 单知识点、多知识点、多题库计划。
- 计划数量与题型/难度分配总和不一致时正确拒绝或按既定规则校验。
- 模型返回非法 JSON、缺少字段、答案不存在、选项重复、知识点 ID 越权。
- 题干完全重复、措辞变化但语义重复、相似但考查角度不同。
- 两个任务并发生成相同内容，落库不重复。
- 生成部分成功/全部失败/任务取消/进程重启恢复。
- 生成的题目状态为 `pending_review`，未发布题目不能组卷。

### 12.2 解析

- 不勾选解析时不调用解析 Agent。
- 勾选解析时主题目生成不等待解析完成。
- 解析成功、失败、重试。
- 管理员手动填写后，旧的解析任务晚到也不能覆盖。
- 已存在 AI 解析再次生成和手动覆盖都有明确行为。

### 12.3 答题记录和统计

- 单选正确/错误、多选完全匹配/漏选/多选、判断正确/错误。
- 简答题未判分不进入客观准确率。
- 同一用户同题首次答错、第二次答对：总提交准确率和首次作答准确率分别符合定义。
- 两名用户答题，独立人数和答题次数不同且正确。
- 同一提交使用相同幂等键重试不重复入账。
- 未登录用户、伪造 user_id、已下架题目提交被拒绝。
- 样本量不足时正确率展示状态正确。

### 12.4 评论

- 登录后发表评论、分页查询、删除自己的评论。
- 未登录发表评论、超长评论、频率超限、伪造 user_id 被拒绝。
- 普通用户不能删除他人评论。
- 管理员隐藏后普通用户列表不再返回；恢复后可见。
- 用户提交 HTML/脚本字符串，数据安全存储且输出端不会执行。

### 12.5 迁移与兼容

- 在已有数据库副本上执行 Alembic upgrade。
- 旧题记录、旧选项、题库关联和知识点关联均保留。
- 新字段对旧记录使用合理默认值；不能把旧题无条件标为已审核发布，需根据当前业务状态定义安全回填方案。
- 迁移后现有知识导入、题库 CRUD、DecisionAgent 接口回归通过。

如果某项依赖当前项目尚未具备（例如普通用户认证或持久化 Worker），不要用临时假数据伪装完成；说明阻塞点和推荐最小实现，先完成不依赖它的部分。

## 15. 同类产品参考与本项目采用的设计原则

以下仅作为产品交互/机制参考，不表示本项目要照搬其商业规则：

1. **LeetCode 题目详情**：官方帮助文档介绍题目页展示 accepted submissions 与 total submissions，并将题目描述、解决方案、提交历史、讨论区分区，同时有随机选题和题目筛选能力。本项目借鉴“统计指标有明确分子分母、答案/讨论分区、筛选和历史记录独立”的信息组织方式。参考：[LeetCode – Start your Coding Practice](https://support.leetcode.com/hc/en-us/articles/360012016874-Start-your-Coding-Practice)。
2. **Codewars 解法与讨论**：官方文档说明用户完成练习后可以查看其他用户解法，并对相似解法进行归组以减少重复；其 Kata 质量流程包含用户反馈、问题报告、审核和下架维护。本项目借鉴“内容需要持续治理、相似内容需要去重、社区反馈需要可处理”，而不是只生成后永久不维护。参考：[Codewars – Solutions](https://docs.codewars.com/concepts/kata/solutions/)；[Codewars – Reviewing a Kata](https://docs.codewars.com/curation/kata/)。
3. **Quizlet Learn**：官方帮助文档介绍练习者可以设置学习目标、选择题型和评分方式，并根据掌握情况使用不同练习模式。本项目借鉴“练习设置和学习反馈应围绕用户目标”，但当前阶段优先把可靠题库、判分记录和统计打稳，不提前做复杂自适应推荐。参考：[Quizlet – Studying with Learn](https://help.quizlet.com/hc/en-us/articles/360030986971-Studying-with-Learn)。

**最终产品判断：** 本项目的核心竞争力首先应是题目可信、答案准确、知识点归属清楚、练习体验稳定、统计口径可信。AI 生成速度和功能数量不能替代题目质量治理。先建立可审核、可追溯、可纠错的题目生命周期，再逐步做自动补题、个性化练习和知识掌握度推荐。
