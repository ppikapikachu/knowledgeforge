# DSH 开发任务：知识导入分块、提取、批次去重与耗时问题排查修复

> 交给 DeepSeek Harness（DSH）执行。
>
> 当前先暂停组题生成，不得推进 QuestionDecisionAgent / QuestionGenerateAgent。优先修复现有知识导入链路。

## 1. 任务目标

修复知识导入任务中的四类问题：

1. TXT 文档分块严重碎片化，题目标题与答案分离，产生极短 Chunk。
2. 知识点提取出现内容省略、无答案题目被伪造成知识内容、模型自行补充原文没有的信息。
3. 同一次导入产生相同名称的候选知识点，未在批次内部可靠去重，或去重结果未在保存前正确生效。
4. 约 11,050 字符的规范 TXT 文件导入耗时约 15 分钟，需要用日志拆分耗时并减少不必要的 LLM 请求。

## 2. 严格范围

- 只修改 `backend/`。
- 不修改 `admin-web/`，不新增前端 API。
- 不开发任何组题生成 Agent。
- 不新增 Redis、Celery、RabbitMQ 等基础设施。
- 修改前先梳理当前工作树实际执行的调用链；不要假设历史文档或旧版 Agent 文件就是服务器当前版本。
- 保留现有 FastAPI、SQLAlchemy、Pydantic、LangChain/LangGraph、MySQL、向量库等技术选型，除非项目实际代码已经不同。
- 先写测试并复现，再修复。避免无关重构。

## 3. 已知复现事实

测试文件：`导入测试.txt`，约 11,050 字符；主题包括 Activity、Fragment、Service、IPC、View 等，每个主题下用 `1、2、3……` 标记面试题，多数答案内容有清晰换行。

服务器分块结果：

- 配置显示 `chunk_size=6000`、`chunk_overlap=500`。
- 实际生成 86 个 Chunk。
- 最大 Chunk 只有 587 字符。
- 21 个 Chunk 少于 30 字符。
- 出现只有 `不同点：` 的 4 字符 Chunk，以及只有 `4）绘制装饰` 的 6 字符 Chunk。
- 题目标题可能独立成为一个 Chunk，答案被拆到后续多个 Chunk。

知识点结果案例：

- 同一导入出现两个 `Activity生命周期`。
- 一个候选的 content 只是“面试题：说下Activity生命周期？（原文仅提出问题，未给出具体生命周期方法内容）”这种占位描述，并非知识答案。
- 另一个候选只保留生命周期方法顺序，遗漏了源文档中对 `onCreate()`、`onRestart()`、`onStart()` 等方法的解释；并额外加入了横竖屏切换、`configChanges`、`ViewModel` 等该题源文没有提供的内容。

注意：这些现象必须以用户提供的原始文档为校验基准，不得把模型常识补充当作原文。

## 5. 分块修复要求

### 5.1 规范 Q&A 文档采用结构感知解析

针对类似本测试文件的面试题文档，识别“题目标题 + 后续答案”这种逻辑单元，而不是把空行直接视作不可跨越的边界。

- 对 `^\s*\d+\s*[、.]` 形式的顶层题目编号进行识别，结合当前章节标题和实际行结构判断题目边界。
- 需要区分题目编号与答案内部的 `1）`、`2）` 等列表项；不要把答案里的子列表误判为新题。
- `Activity`、`Fragment面试题`、`Service面试题`、`IPC面试题`、`view面试题` 等章节标题应作为上下文/分类，不应单独提取为知识点。
- 题目标题及它的所有答案段落必须归属同一逻辑块，直到识别到下一个顶层题目或新章节。
- 不要要求题目标题和答案之间必须有空行；有些标题会直接跟在上一题最后一行之后。
- 对同一逻辑块保留源文原始文本或可追踪的稳定 block ID，便于定位及审核。

### 5.2 根据逻辑块聚合 Chunk

- 先识别逻辑题目块，再把多个完整题目块聚合到目标大小约 6,000 字符的 Chunk。
- `chunk_size` 应成为有效的目标大小/上限策略，而不是配置为 6,000，输出却全部是几十或几百字符。
- 尽量只在题目块边界切分；不要把一个题目和它的答案拆开。
- overlap 只能在不破坏题目单元的前提下使用，不能复制导致重复抽取大量候选。
- 通用文档回退模式也必须在切割后合并过短段落；空白段落不允许单独成为 Chunk。
- 增加最小 Chunk 长度保护。只有章节标题、`不同点：`、`4）绘制装饰` 等短片段不应单独作为知识提取输入。若片段本身只是标题或列表引导词，应与相关内容合并；纯目录/页眉等内容可以被过滤。
- 不能通过简单全局替换双换行来糊弄修复；必须保留章节、题目、答案和列表结构。

### 5.3 分块验收

用原始测试文件自动化验证：

- 每道有答案的编号题，其标题和答案留在同一逻辑块中。
- `不同点：` 与后面的区别说明不能分成彼此无关的输入。
- `4）绘制装饰` 必须留在 View 绘制流程的答案上下文中。
- 不应再出现 4、6 字符等孤立 Chunk。
- 11,050 字符的输入不应继续产生 86 个碎片化 Chunk；具体 Chunk 数量按逻辑块和目标大小确定，不要求硬编码固定数量。
- `char_start`、`char_end` 必须和 `full_text` 的真实字符位置一致；如果文本归一化改变了偏移计算，应统一策略并测试。
- 对 PDF/DOCX/MD 的既有分块路径补回归测试，不要以 TXT 优化破坏其他文件格式。

## 6. 知识点提取修复要求

### 6.1 对结构化 Q&A 文档优先保留原文

当文档可可靠识别为编号问答格式时：

- `name` 基于题目标题生成，去除题号和多余空白；可以规范化问句表达，但不能改变主题。
- `content` 必须完整保留该题对应的源答案，包括方法列表、解释、条件、例子和注意事项；第一版优先使用原文，不要让模型重新撰写或压缩答案。
- 如果需要 `summary`、`keywords`、`difficulty` 等字段，可从整批题目中集中生成元数据，但元数据生成不能改写或覆盖原始 `content`。
- 提取提示词应明确：不得省略有意义的子项；不得外推原文没有的结论；不得新增“横竖屏切换”“ViewModel”等原文不存在的事实；不要把题目标题改写成答案。
- 对普通散文或非结构化资料可保留通用 LLM 提取路径，但也必须要求内容有源文依据并保留关键细节。

### 6.2 没有答案的题目如何处理

若某道编号题之后没有实质性答案：

- 不要生成“原文仅提出问题，未给出具体内容”这种占位知识点并正式入库。
- 不要让模型根据常识自行补齐答案。
- 标记为 `insufficient_source` / 待人工处理，或按现有数据模型以最小改动记录跳过原因。
- 如果现有模型没有该状态，不要顺手大规模改表；可以先记录在任务结果/日志中，除非当前业务必须持久化该状态。

### 6.3 防止短 Chunk 产生虚假候选

在 LLM 前增加简单、确定性的输入检查：

- 纯章节标题、纯“不同点：”等缺乏完整语义的文本，不调用 LLM 或要求输出空候选。
- 不得仅因 Schema 中字段非空就把低质量候选视为通过验证。
- 在保存前校验 candidate 的来源文本确实包含对应的知识信息。可采用源块归属、源文本覆盖/关键短语验证等轻量方法；不得要求内容与原文逐字完全一致到连正常空白整理都无法通过。

## 7. 批次内部去重及数据库去重修复

必须明确区分两层：

1. **批次内部去重**：对本次导入全部抽取的 candidates 去重。
2. **数据库去重**：对批次去重后的候选，再检索当前知识库已有内容。

正式入库前必须先执行第 1 层，不得把“查过数据库”视为“批次内部去重”。

具体要求：

- 对名称进行统一标准化：Unicode/大小写/全半角/空格/标点等差异不应导致明显重复绕过检查；不要简单全局 `name UNIQUE`。
- 同一知识库范围内，标准化名称完全相同的候选必须进入确定的合并/冲突处理逻辑，不得无条件作为多条 NEW 保存。
- 候选的相似度比较不能只比较 name，也要结合 summary、content、keywords 和 source block。
- 对同名不同内容的候选，先回溯源块：若是一题被多个 Chunk 重复抽取，只保留一个候选，并以完整源答案为准；如确属不同内容，标为冲突/需要审查，不要静默覆盖。
- 语义相似候选继续使用现有 Embedding/Vector DB 和 Deduplicate Pipeline；不要为了修复新增另一套相互冲突的去重系统。
- 如果 Vector DB 同步发生在批次全部 MySQL 保存之后，则本批次候选不能依赖 Vector DB 来彼此去重，必须先做内存/数据库批次去重。
- 同一次导入中的候选应先全部收集，然后批次去重，再对数据库进行查重和持久化。
- 保留 `knowledge_base_id` 过滤，不能把不同知识库的知识混在一起判断。
- 去重完成后输出明确统计：原始候选数、批次内重复数、数据库重复数、合并数、新增数、跳过数、冲突数。

## 8. 耗时排查与优化

已知旧版 Agent 代码采用 LangGraph 条件边逐个处理 Chunk，`extract_current_chunk_node` 每次仅处理一个 Chunk，配置 `AGENT_MAX_RETRIES=2` 意味着单 Chunk 最多会尝试 3 次。若 86 个 Chunk 都执行 LLM，单是抽取就可能有 86 次成功调用，并可能有额外重试；这很可能解释了总耗时的一大部分。请核对服务器当前代码后确认，不能只凭推测下结论。

必须记录每个阶段的：开始时间、结束时间、耗时、处理数量、调用次数、失败/重试次数。至少包含：

- parse_document
- chunk_document
- extract_llm（调用总数、成功、失败、重试；逐 Chunk 耗时）
- candidate_batch_dedup
- embedding
- vector_search / database_dedup
- save_knowledge
- 总耗时

性能优化顺序：

1. 先修分块，减少无意义的 LLM 调用。
2. 再减少缺少上下文的无效提取和不必要重试。
3. Embedding 尽可能批量请求，不应对每条知识点无必要地单独请求。
4. 检查向量检索和数据库去重是否逐候选重复执行昂贵操作。
5. 在当前 API 响应问题已修复的前提下，再考虑受控并发；不能直接无限并发，也不能重新导致 FastAPI 登录/其他 API 超时。
6. 不要把 LLM 调用放在持有长事务或数据库连接的区间内。

以同一测试文件、同一模型服务和同一网络进行修复前后对比。15 分钟对于约 11K 字符的规则化 TXT 不是理想表现；但具体耗时由模型供应商、网络和后续去重/Embedding 决定，因此必须提供各阶段实际耗时，不要只给一个总时间。
