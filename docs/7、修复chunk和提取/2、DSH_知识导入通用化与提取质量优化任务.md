# DSH 任务文档：知识导入通用化与提取质量优化

> 执行对象：DeepSeek Harness（DSH）  
> 工作范围：仅后端 `backend/` 目录（以当前仓库实际目录为准）  
> 当前目标：修复并验证知识导入链路，不开发组题生成，不修改 `admin-web/` 前端。  
> 重要约束：先检查当前工作树和真实调用链，再决定修改点；本文给出目标和验收标准，不要求照搬示例数据结构，也不允许只针对本次 TXT 文件写特殊逻辑。

---

## 1. 任务背景与当前已知问题

最近一次测试文件为 `导入测试.txt`，原文约 11,050 字符，包含 Android 面试资料。原有分块结果产生 86 个 Chunk，出现 4 字符、6 字符等没有独立语义的小 Chunk。修复后 Chunk 数量变成 2 个，长度分别约 5,958 和 5,112 字符，明显减少了碎片化，但仍需要验证章节上下文、来源偏移和大批量提取是否可靠。

此前暴露的问题：

1. 文档分块过度依赖空行/段落边界，短段落没有合理合并。
2. 知识点名称相同，但内容不同的候选可以同时出现；必须确认去重是否覆盖“本批候选之间”以及“与数据库已有知识之间”两个范围。
3. 模型会将原文内容过度概括，例如只保留生命周期顺序，却丢失每个方法的用途说明；也可能添加原文没有的内容，例如横竖屏切换、`configChanges`、`ViewModel`。
4. 对于只有题目、没有答案的条目，不能生成“原文仅提出问题……”这种占位文本作为正式知识内容。
5. 分块数量少不等于提取质量高。单个大 Chunk 中含多道题时，可能发生题目/答案错配、跨主题干扰、输出截断或内容压缩。
6. 性能尚未通过真实运行数据验证。之前一次导入耗时约 15 分钟；修复报告估算 2 分钟，但估算不能替代实测。
7. 输入格式未来会多样化：编号问答、Markdown、`*`/`□` 等符号列表、只用空行分隔的段落、单换行文本、没有明确标记的连续文本，以及它们的混合形式。系统不能围绕当前这一份编号问答 TXT 写死逻辑。

## 2. 本次总体目标

建立通用、可扩展、可观测的知识导入流程：

```text
多格式文档
  ↓
解析与保真规范化
  ↓
通用结构/边界识别（可识别，也允许未知）
  ↓
Document Unit（临时中间单元）
  ↓
按输入/输出预算自适应组批为 Chunk
  ↓
Knowledge Extract Agent（单元级来源绑定、批次内相互隔离）
  ↓
提取质量验证
  ↓
本批候选内部去重/冲突处理
  ↓
与数据库已有 Knowledge 比对
  ↓
NEW / DUPLICATE / MERGE / REVIEW 或现有等价状态
  ↓
现有正式入库流程与向量同步
```

本次应优先解决正确性，其次降低不必要的 LLM 调用和总耗时。不要为了追求最少 Chunk 数量而牺牲完整性，也不要为每个短段落单独调用模型。

## 3. 开始修改前必须完成的调查

先检查服务器/当前工作树正在使用的实现，不得假设之前某个文件版本就是实际运行版本。

至少检查：

- `DocumentParser` 的 TXT/MD/DOCX/PDF 解析路径，以及 `full_text` 的拼接方式。
- `TextChunker` 当前 `chunk()` 和相关辅助方法，特别是 Q&A 检测、短块合并、长度计算、`char_start`/`char_end`、`chunk_size`/`chunk_overlap` 的真实语义。
- `DocumentChunk`、提取结果和 `KnowledgeCandidate` 的实际 Schema。
- `KnowledgeExtractAgent` 的 Prompt、每次模型调用方式、`max_tokens`、重试条件、结构化输出以及响应截断检测。
- 正式 ImportTask 当前调用的 Extract、候选批次去重、数据库去重、保存和向量同步代码；确认运行时没有绕过修复后的实现。
- `batch_dedup.py` 对同名不同内容、别名、语义相近候选、候选间去重和数据库已有知识分别做了什么。
- 任务日志、进度、各阶段耗时和异常记录是否足以复现问题。

先输出简短根因清单，再按本文验收标准实施修复。保留现有可用业务和 API；除非证明必要，不大规模重构数据库或整个架构。

## 4. 通用解析与中间数据结构

### 4.1 不得把某一种格式当作唯一格式

至少考虑以下输入：

1. **编号问答**：`1、问题`、`2. 问题` 等，问题和答案可能由空行分隔，也可能紧邻。
2. **符号列表**：以 `*`、`□`、`-`、`•` 等开始的列表项。符号可能只是格式，也可能出现在普通正文中，不能看到符号就无条件拆分。
3. **标题/Markdown**：`#`、`##`、章节标题、代码块和列表等。
4. **空行分段**：每个自然段用一个或多个空行隔开，但并不保证一段就是一个知识点。
5. **单换行文本**：连续多行，可能每行是列表项，也可能是同一段答案的续行。
6. **无明确标记文本**：仅靠句子、标点、语义和长度判断边界。
7. **混合文档**：文档中不同章节使用不同格式。

### 4.2 保留原文与非破坏性规范化

- 原始文本必须可追溯；换行符归一化、空白清理等操作不得使原文内容静默丢失。
- 如果规范化后的字符位置与原始文本位置不一致，不能继续把规范化文本中的下标冒充原文偏移。应建立映射，或清楚定义并测试偏移属于哪一份文本。
- 过滤版权声明、重复页眉/页脚、明显无关的 URL 等内容时，只能在高置信度规则下过滤；保留原始文本和来源范围以便审计。
- 不要直接删除所有章节标题。标题默认作为可选上下文元数据传递，而不是知识点内容；模型不能只凭标题生成知识点。
- 题目标题是问题的一部分，应保留；不可与章节标题混为一谈。
- 没有标题时字段允许为 `null`，不能要求每个单元必须有标题或题目。

### 4.3 Document Unit 是内部抽象，不是新的正式知识库表

建议用现有可行的内部 Pydantic 模型或 dataclass 表示通用单元。下面只是字段设计参考，不要求照搬字段名：

```json
{
  "unit_id": "unit_xxx",
  "text": "该单元的原文文本",
  "source_start": 0,
  "source_end": 120,
  "unit_kind": "paragraph | qa | list_item | heading | sentence | unknown",
  "section_context": null,
  "marker": null,
  "boundary_confidence": 0.0
}
```

要求：

- `unit_kind` 是识别结果和提示信息，不是硬性的输入前提；不能识别时使用 `unknown`，仍然继续处理。
- 不要因为引入中间单元就新增一套与正式 `knowledge` 重复的数据库表。
- 现有正式 Knowledge Schema 尽量保持稳定；优先把单元结构用于解析、分块、提示词上下文和来源追踪。
- 允许一个单元没有标题、编号、标记；允许一个单元中包含多句或多个相互依赖的列表子项。

## 5. 通用边界识别与自适应分块

### 5.1 分层识别策略

优先使用确定性且可解释的规则识别高置信度边界；低置信度时不要强行作出“这是一个独立知识点”的结论。

建议识别顺序：

1. 解析格式自带的结构（Markdown 标题、列表、代码块、文档段落等）。
2. 识别常见问题编号和列表标记，但区分顶层题号与答案正文中的子项编号。
3. 使用空行、段落、句子边界作为通用线索。
4. 对仍然存在歧义的内容，保留为较大的原文单元并让 Extract Agent 判断；只有在确有收益时才考虑增加低置信度的模型辅助边界识别，避免无意义地增加一次全量 LLM 调用。

不要使用“只按 `\n\n` 切割”的方案；也不要使用“每遇到 `*`/`□`/数字就新建知识点”的单条规则。

### 5.2 按目标长度聚合，不机械切碎

- 先识别相对完整的单元，再将多个单元聚合成 Chunk。
- `chunk_size` 是目标长度/预算，不代表每个 Chunk 都必须精确达到该长度。
- 默认不能生成只有几个字符的 Chunk。若一个短单元是标题，应与它所属的正文绑定；若是答案中的子列表，则与其父单元合并。
- 极短单元只能在不存在合理父单元、也无法安全合并时单独保留，并须有原因日志；不能静默产生大量无意义短 Chunk。
- 如果一个完整单元本身超过目标长度，才考虑在自然段/句子边界拆分，同时保留父单元 ID、原文偏移和必要上下文；避免在句子中间或题目与答案之间随意切断。
- `chunk_overlap` 只能用于确实需要的上下文连续性。由于重叠内容会引入重复候选，必须依赖来源 ID 和去重处理，不能忽略重叠引起的重复。
- 每个 Chunk 可拥有多个 Document Unit 的 ID/来源范围，不应仅靠单个 `title` 字段表达混合主题的所有上下文。
- 不要把“Q&A 分块”作为系统唯一工作方式。它是通用结构识别中的一种高置信度策略。

### 5.3 原文覆盖和偏移必须可测试

增加自动化测试，至少保证：

- 所有有效原文内容都被某个单元/Chunk 覆盖。
- 不因分块而遗漏或重复非 overlap 内容。
- `source_start`、`source_end`、`text_length` 的关系符合明确约定。
- 如果输出文本经过规范化或补充分隔符，必须清楚区分原文范围和 Chunk 展示文本长度。
- 章节标题不需要成为知识点正文，但其上下文必须能传给所属内容。

不要只靠 `chunk_count == 2` 判断本测试文件分块正确。不同策略可能得到不同数量的合理 Chunk；重点是完整性、边界质量、长度预算和提取效果。

## 6. 提取 Agent：单元边界与来源隔离

### 6.1 不要只对单个大 Chunk 做无约束的整体提取

一个 Chunk 可以包含多个单元；单次模型调用也可以处理多个单元，但 Prompt 和输入必须明确区分单元。建议优先实现：

- 把一个批次中的 Document Unit 分别带上 `unit_id`、可用的章节上下文、原始文本和来源范围。
- 要求模型对每个单元独立判断，允许返回 0、1 或多个候选知识点。
- 每个候选必须关联明确的来源 unit ID；如果一个知识点确实依赖多个单元，应明确返回多个来源，而不是默认跨单元自由拼接。
- 不允许以另一个单元的内容补全当前单元；不允许将相邻题目的答案归到同一知识点。
- 标题/章节上下文用于帮助理解，不得单独形成知识点；题目标题可以用于确定名称，但不能冒充答案内容。
- 没有标题或编号的段落照样可以提取，不允许因缺少元数据而跳过有效内容。

### 6.2 依据输入和输出 Token 预算组批

不要把每次 3～5 道题或 6000 字符固定成永远不变的规则。可以先用小批次进行测试，但实际批次规模应由配置和观测数据决定：

- 输入 Token 长度/估算值。
- 预期输出 Token 数量（候选数量、每个候选完整内容、摘要、关键词等）。
- 模型上下文限制和 `LLM_MAX_TOKENS`。
- 之前同类批次的输出规模与响应时间。
- 是否存在特别长的单元。

当预计输出过大时，优先减少每个批次中的单元数量，而不是依赖模型自动压缩内容。超长单元应按自然边界安全处理，不能直接丢掉后半部分。

### 6.3 原文忠实度和内容完整性

Prompt 必须明确区分 `summary` 和 `content`：

- `summary` 可以用少量句子概括。
- `content` 必须保留原文中与该知识点有关的关键细节：定义、步骤、方法/参数说明、条件、例子、列表项、优缺点及原文中的必要限定。可以整理格式，但不能为追求简短而省略关键细节。
- 不能新增输入中不存在的知识。例如原文未提及的横竖屏切换、`configChanges`、`ViewModel` 不允许在提取时自行补上。
- 如果原文信息不足，只能提取原文已支持的部分；不能把通用常识补入 `content` 伪装成原文。
- 对于只有问题、没有答案的条目，不要生成“原文仅提出问题……”这种占位知识内容；使用已有的跳过/待处理/警告机制。如果现有结果 Schema 没有合适状态，优先在任务结果或错误报告中记录，不要为了这次任务随意大改正式知识表。
- 不要要求 `content` 必须和原文逐字完全一致，因为可能需要结构化；但原文中的重要信息不得丢失，来源必须可以回查。

### 6.4 输出验证、截断和重试

- 检查模型响应是否成功完成、结构化 Schema 是否通过、来源 unit ID 是否有效、候选字段是否完整。
- 若服务商提供 finish reason 或类似元数据，应检查是否有输出长度截断。
- 不要把“JSON 结构合法”当作“内容完整正确”。
- 可以加入内容完整性启发式检查，例如原文单元很长但 `content` 极短、候选数明显不足、来源 ID 缺失、输出接近 Token 上限时标记警告。阈值应可配置并通过测试验证，避免只靠固定比例误判。
- 如果输出截断或批次输出超限，应该将当前批次拆小重试；不要用同一份过大的输入重复请求多次。
- 重试次数必须有上限，日志应记录重试原因、次数和实际耗时。

## 7. 批次内部去重与数据库去重

候选去重必须分为两个清晰阶段：

```text
所有候选
  ↓
本次导入候选内部去重
  ↓
与数据库已有 Knowledge 比较
  ↓
NEW / DUPLICATE / MERGE / REVIEW（按现有业务状态兼容）
```

### 7.1 批次内部去重

- 必须对本次任务生成的候选全集去重，不能只对数据库查询结果去重。
- 先做名称规范化和精确匹配，再根据现有 Embedding/Vector 和语义去重实现处理近似候选。
- 同名且内容高度重复的候选不能都保留为新知识。
- 同名但内容不同，不等于一定重复，也不等于一定可以直接覆盖。要判断它们是同一知识点的补充、不同侧面还是实质冲突。
- 内容互补时，合并后的 `content` 必须保留有来源支持的细节；不能简单保留第一个/最短/随机的内容后丢掉其他有效答案。
- 内容实质冲突或来源不明确时，保留冲突信息，标记人工复核/候选冲突；不要把不同版本静默合并成一个看似确定的答案。
- 不能只根据名称去重而不检查内容和来源；也不要简单地把不同名称一律当作不同知识。
- 如果使用相似度阈值或内容差异比例，配置要有依据并通过测试验证。不能把“内容差异超过 50% 就无条件保留先出现版本”作为普遍正确的策略。

### 7.2 数据库已有知识去重

- 保留当前 MySQL 为正式数据源、Vector DB 为检索索引的既有设计。
- 批次内部去重后，才逐个或批量检查现有数据库/向量库。
- 如果已有的 DeduplicatePipeline 定义了 `NEW / DUPLICATE / MERGE`，尽量兼容现有状态；确有必要引入 REVIEW 时先评估对当前 API 和任务统计的影响。
- Vector 搜索或 Embedding 不可用时，不能假装“未发现重复”并批量创建新知识。应按现有失败策略记录错误、阻断危险的写入或进入安全的待复核状态。
- 持久化仍走现有 KnowledgeService 和正式表；不要新建另一套知识主表。

## 8. 性能与日志：以真实测量为准

针对每个 ImportTask 记录可诊断的数据，至少包括：

- 文档解析耗时。
- 规范化/边界识别耗时、识别到的单元数。
- 分块耗时、Chunk 数量、长度分布（最小/平均/最大）、过短块数量。
- 提取调用次数、每次输入长度或 Token 估算、输出 Token（若服务商可提供）、耗时、重试次数、成功/失败和截断情况。
- 提取候选数量、按来源单元统计的候选数、无答案跳过数、验证失败数。
- 批次内部去重耗时与数量变化。
- Embedding、Vector Search、MySQL 查询和保存的耗时/调用次数。
- 最终 NEW / DUPLICATE / MERGE / REVIEW / FAILED 数量，以及任务总耗时。

15 分钟对于约 11,050 字符的简单 TXT 导入显然值得优化，但不能只承诺“修复后 2 分钟”。先通过实测确定瓶颈，再判断目标。减少无意义 Chunk 和不必要的重试通常比盲目增加并发更应优先。不要为本次任务新增 Redis/Celery/RabbitMQ 等新基础设施。

## 9. 必须新增或更新的测试

请使用自动化单元测试/集成测试覆盖多种格式，不可只测试本次 `导入测试.txt`。建议在现有测试目录增加清晰、可复用的 fixture。

### 9.1 测试输入格式

至少包含以下 fixture：

1. **当前原始编号问答 TXT**：题目编号清晰，答案有多行、空行和答案内部子项。
2. **符号列表**：以 `*`、`□`、`-` 等开头；同时包含正文中出现类似符号的情况，验证不会无条件误切。
3. **Markdown 文档**：多级标题、列表、代码块、段落混合。
4. **空行分段纯文本**：没有编号和章节标题，一段可能是一个知识点，也可能需要和相邻段落合并。
5. **只有单换行的文本**：多行连续文本，部分行是同一答案的续行。
6. **没有明显分隔符的连续文本**：基于句子边界和上下文处理，无法判断时允许不确定，不得凭空造边界。
7. **混合格式文档**：标题、编号问答、列表和纯文本并存。
8. **超长单个单元**：测试超过目标 Chunk 大小时安全拆分，不丢失后半内容。
9. **无答案题目**：问题后没有答案，验证不会把占位解释写入 Knowledge。
10. **重复候选**：同一批次内出现同名同内容、同名内容互补、同名内容冲突、不同名但语义高度相近的候选。

### 9.2 分块验收标准

- 不允许因空行或换行产生大量几字符的 Chunk。
- 标题、列表标记、编号只有在确认为结构边界时才影响切分；未知格式仍可正常处理。
- 原文覆盖和字符偏移可验证；不能静默丢失或复制非 overlap 内容。
- 长单元切分必须遵循自然边界，并维持单元 ID 和来源映射。
- 不将固定 Chunk 数量作为通用验收标准；对每个 fixture 检查边界、长度、覆盖和来源。

### 9.3 提取质量验收标准

使用可控 mock 测试来验证流程行为，并提供真实 LLM 的手工/集成验证结果：

- 不要求每个 Chunk 都必须生成知识点。
- 任何候选都能追溯到有效源单元。
- 每个题目的答案不串到另一题；不同单元的内容不能隐式互相补全。
- 长答案不会在输出或后处理时被无提示地截断。
- `summary` 可以概括；`content` 保留所有关键细节且不添加无来源的事实。
- 无答案的条目不会产生占位 Knowledge。
- 单个批次允许产生零/一个/多个候选。

### 9.4 去重验收标准

- 同一批次内同名同内容候选不能重复保存。
- 同名内容互补时，保留所有有来源支持的关键内容。
- 同名内容冲突时不静默丢弃其中一个来源；产生可审计的冲突/复核结果。
- 第二次导入同一份文件时，不应再次创建大量重复 Knowledge。
- 已有测试库中的相关知识仍能被正确检索，不影响其他知识库的数据隔离。

### 9.5 性能验收标准

- 使用真实测试文件进行端到端计时并记录各阶段耗时和调用次数。
- 解释修复前后耗时差异来自哪里，不仅给一个总时长。
- 若真实 API 慢，提供每次调用耗时分布、重试原因、输入/输出 Token 数据（可获取时）来证明瓶颈。
- 不允许在没有实测的情况下将预计耗时写成“实测结果”。

## 10. 实施边界与兼容性要求

- 只修改后端目录；禁止修改 `admin-web/`、客户端或与本任务无关的功能。
- 不要开始开发组题生成相关功能。
- 不要重建正式 Knowledge 数据表；尽量沿用已有 Pydantic Schema、KnowledgeService、DeduplicatePipeline、ImportTask 状态和 API。
- 如果确实需要 Schema/数据库迁移，先说明原因和兼容影响，尽量用最小变更；不能为了保存临时 Document Unit 而重复建立正式知识表。
- 不要把当前编号问答的正则逻辑写成所有文档唯一的解析方式。
- 不要为了追求最少 Chunk 数而把整个文件一次性塞给模型。
- 不要为了追求最少模型调用而允许输出内容被压缩或截断。
- 不要默默删除来源文本；过滤行为要可解释、可测试、可追溯。
- 保持现有日志可读，并补充必要的阶段统计。

## 11. 执行顺序

建议按以下顺序执行，并在每一阶段完成后跑对应测试：

1. 检查当前实际调用链，输出根因清单和修改计划。
2. 定义并测试通用 Document Unit/来源映射（尽量使用内部结构，不改正式知识库表）。
3. 实现多格式通用边界识别和自适应 Chunk 聚合，先通过所有分块 fixture。
4. 调整 Extract Prompt 和单元来源绑定，增加内容完整性、截断、来源校验。
5. 修复批次内部去重及与数据库去重的衔接，加入冲突处理。
6. 加入各阶段耗时、调用数量与错误指标。
7. 对当前 TXT 和其他格式做自动化及真实 LLM 集成测试。
8. 运行完整后端回归测试，确认 Auth、Knowledge、Question、ImportTask、Dashboard 等现有功能未被破坏。

## 12. DSH 交付物

完成后必须给出：

1. **根因与修改总结**：具体说明真实执行路径、每个问题的原因、改了哪些文件以及为什么改。
2. **测试结果**：执行的命令、通过/失败数量、失败用例原因；不能只写“测试通过”。
3. **多格式回归结果**：每类 fixture 的原始长度、单元数、Chunk 数及长度分布、覆盖/偏移检查结果。
4. **提取质量验证**：原始有答案条目数、提取候选数、缺失/跳过/重复/冲突数；抽样对比原文与 `content`。
5. **真实性能报告**：解析、边界识别、分块、提取、去重、Embedding/向量检索、保存的实测耗时和 LLM 调用/重试数。明确区分实测和估算。
6. **兼容性说明**：是否改了正式 Schema、数据库迁移、API 或配置项；如有，说明回滚和兼容方式。
7. **已知限制**：说明哪些无法可靠自动判定，尤其是没有结构标记的连续文本如何降级处理。

## 13. 最终验收定义

只有同时满足以下条件，才可以将知识导入链路标记为本阶段完成：

- 通用解析不依赖单一题号/标题/标记格式。
- Chunk 不再产生大量无意义短块，并且原文覆盖与来源偏移可验证。
- 标题用于上下文而不误生成为知识；没有标题的内容也能正常提取。
- 多单元批量提取时，输出候选与来源单元绑定，减少跨单元污染。
- 内容没有被无提示地过度压缩或凭空补充。
- 批次内部去重先于数据库去重，重复、互补和冲突有不同处理方式。
- 性能瓶颈通过实测数据定位，修复效果有可核对的调用次数和阶段耗时。
- 后端回归测试通过，前端及组题功能没有被修改。

**本任务完成前，不要进入组题生成阶段。**
