请先检查 `admin-web/` 当前 Vue3 项目结构、路由、侧边栏、API 请求封装、类型定义、状态管理和现有页面样式。在现有设计系统和组件风格中增量实现，不要重建前端项目或换 UI 框架。

先从后端交付说明/现有 API 定义中确认实际的：

- Knowledge 列表按 `knowledge_base_id` 查询的参数名。

- ImportTask 列表/详情中的知识库字段。

本文给出的 API 路径是目标契约示例。如果 DSH 的已实现路径、字段或响应结构不同，应根据后端真实契约适配前端并指出差异；不能因此修改后端代码。若后端还未实现必要接口，请列出缺失接口并等待/通知后端负责人，而不是在前端伪造真实数据或增加 API。

## 1. 产品目标

让管理员能够清楚地管理多个知识领域，例如 Android、Java、分布式系统、C 语言，并完成：

1. 查看当前有哪些知识库，以及各库知识点数量。
2. 点击一个知识库进入该库的知识点列表。
3. 查看、搜索、分页和维护当前库的知识点。
4. 新建或编辑知识点时选择所属知识库。
5. 上传/导入文档前必须选定目标知识库。
6. 查看导入任务时，明确展示任务所属知识库。
7. 管理员可以创建、编辑、停用知识库；不允许在有内容时进行破坏性删除。

用户端多知识库混合练习、随机出题和答题界面不属于本阶段。

## 2. 推荐信息架构

尽量沿用现有菜单；在现有导航中增加一个“知识库”入口，点击后显示知识库概览。

### 页面 A：知识库列表/概览

展示知识库卡片或表格行：

- 名称：Android、Java 等。
- 简短描述。
- 知识点数量。
- 状态（正常/停用）。
- 进入知识点按钮或整行可点击。
- 创建/编辑/停用操作。

点击某库后进入知识点列表，并携带 `knowledge_base_id` 作为筛选条件。默认不要把所有库的知识混在一个列表里；如保留“全部知识库”视图，必须清楚显示当前筛选状态。

### 页面 B：知识点列表

在现有知识点管理页上增量增加：

- 页面标题或面包屑显示当前库名称，例如 `知识库 / Android / 知识点`。
- 可见的知识库切换控件，切换后重新请求当前库数据。
- 搜索、状态筛选、分页等已有功能保持正常。
- 每条知识点可见其归属（若当前页面允许跨库全局列表）。
- 新建/编辑抽屉或弹窗增加“所属知识库”选择器。
- 保存成功后刷新当前库的列表与计数。
- 对从一个库移动到另一个库的操作，需要二次确认并提示向量索引会由后端同步；不能由前端直接操作 Vector DB。

如果当前页面结构更适合在知识点页顶部放知识库卡片/Tab，可保留这种实现，但必须满足“点击不同库查看对应知识点”的核心流程，并支持直接进入指定库。

### 页面 C：导入任务

在上传文件/创建任务表单中增加必选“目标知识库”：

- 只允许选择状态正常的知识库。
- 未选择时前端表单校验阻止提交并给出清楚提示。
- 请求中发送后端契约定义的 `knowledge_base_id`。
- 任务列表和详情显示知识库名称，用户不需要通过 ID 猜测任务属于哪一库。
- 任务失败、重试、进度展示等现有行为不得破坏。

### 页面 D：知识库管理

可在概览页通过创建/编辑弹窗实现，不强制再增加一张复杂页面。字段至少有名称、稳定 code（创建时填写/由后端生成，按 API 契约决定）、描述、状态。

- 不允许重复 code/name（具体唯一规则跟随后端验证）。
- 有知识点或任务引用的库不可硬删除；前端优先提供停用/启用。
- 停用有确认提示，并从新建导入的可选项中移除。

## 3. API 对接约定

建议对照真实后端契约使用以下接口（如实际路径不同，以后端为准）：

- `GET /api/v1/knowledge-bases`
- `GET /api/v1/knowledge-bases/{id}`
- `POST /api/v1/knowledge-bases`
- `PUT/PATCH /api/v1/knowledge-bases/{id}`
- `PATCH /api/v1/knowledge-bases/{id}/status`
- `GET /api/v1/knowledge?knowledge_base_id={id}`
- `POST /api/v1/import-tasks`，body 包含 `knowledge_base_id`

必须复用现有请求封装、鉴权 token、统一响应处理、错误提示和 TypeScript 类型风格。不要直接在 Vue 组件中散落重复请求 URL；如项目已有 API modules，继续按其方式组织。

如果后端列表只返回分页数据，请使用服务端分页；不要为了展示一个库而拉取所有知识点再在浏览器端筛选。

## 4. 交互与状态要求

- 切换知识库时，重置分页至第一页，清理不兼容的筛选条件并重新加载列表。
- 页面加载要展示 loading 状态；空库显示友好空状态及“导入文档/新建知识点”入口。
- API 错误要展示可理解的错误信息，不要把错误显示成“0 条数据”。
- 创建/编辑/停用操作给出成功/失败反馈。
- 停用知识库后，刷新列表和所有选择器选项。
- 导入任务详情以服务端保存的 `knowledge_base_id`/名称为准，不使用用户当前页面选中的库覆盖历史任务归属。
- 不要把“未分类”当作正常用户默认选择；只有兼容旧数据和必要的管理场景需要展示它。
- 响应式布局维持现有管理后台风格；不要引入无关视觉重设计。

## 5. 历史数据管理

DSH 迁移会将历史 Knowledge 放到“未分类”。前端应能够：

- 进入“未分类”查看历史数据。
- 编辑单条 Knowledge 的归属。
- 如数据量较大且后端提供批量转移接口，可提供批量选中并转移到指定库的操作；如果没有后端接口，本阶段不要在前端假装支持批量转移，也不要自行添加接口。

移动归属时显示明确警告：“调整归属会影响该知识点参与去重和检索的范围”。如后端提供操作结果或同步状态，应展示后端真实返回值。

## 6. 视觉规范

- 跟随当前项目已有颜色、字体、间距、按钮、表格、弹窗和空状态规范。
- 知识库卡片以简洁的信息层级展示名称和知识点数量，不要使用过多高饱和色。
- 当前选中库要有清楚但克制的选中状态。
- 不要把“知识库”做成纯装饰性标签；它必须真正控制后端请求的筛选参数。
- 使用项目现有的 UI 组件；除非项目已使用，否则不要再引入新的大型 UI 组件库。

## 7. 验收流程

在后端服务运行的情况下，实际操作验证：

1. 打开知识库列表，能够看到 Android、Java、分布式系统、C 语言和未分类等服务端实际返回的知识库。
2. 点击 Android，只展示 Android 的 Knowledge；切换 Java 后只展示 Java 的 Knowledge。
3. 在 Android 库新建 Knowledge，重新进入 Java 库后不应看到这条记录。
4. 新建导入任务时必须选目标知识库，未选择无法提交。
5. 选择 Android 上传文件后，任务列表与详情都显示 Android。
6. 切换到停用库时，不能为该库创建新导入任务。
7. 已有知识点的新建、编辑、删除/软删除、搜索、分页等功能回归正常。
8. 创建、编辑、停用知识库功能与服务端 API 实际联通。
9. 不使用硬编码 mock 假装接口成功；仅测试专用 mock 不得进入正常生产流程。
10. 现有前端 lint/typecheck/build（以项目实际 scripts 为准）通过。
