# AI 面试题库系统：知识库分类与关系集成执行顺序说明 V1.0

## 1. 结论

建议现在先增加“知识库/领域”归属，再做 `KnowledgeRelationAgent` 的正式导入集成。

原因：知识库归属会直接影响以下逻辑：

- 上传文档时，确定本次知识属于 Android、Java、分布式系统、C 等哪个领域。
- 知识去重时，限定优先比较当前知识库中的已有知识，避免不同领域误合并。
- 关系 Agent 检索候选时，默认只检索同一知识库，避免跨领域产生大量不相关关系。
- 管理员按知识库筛选和维护知识点。
- 后续练习/出题模块按一个或多个知识库筛选题目，例如 Android 单领域，或者 Android + C 混合练习。

如果先完成关系集成，再引入知识库，会需要重新调整 ImportTask 参数、去重检索、向量元数据、关系候选检索和后台筛选。现在加是小范围增量改造，不需要推翻现有 Agent。

## 2. 重要建模决定：知识库不是普通知识点

不要把“Android”“Java”“C语言”当作普通 `knowledge` 记录插入，再依靠 `knowledge_relation` 把它们做成树根。

V1.0 建议新增独立的 `knowledge_base`（知识库/领域）实体：

```text
knowledge_base
  ├── Android
  │     ├── Activity 生命周期
  │     ├── Binder
  │     └── Handler
  ├── Java
  │     ├── 集合框架
  │     └── Java 多线程
  ├── 分布式系统
  ├── C 语言
  └── 未分类（用于兼容旧数据和异常兜底）
```

每个知识点在 V1.0 只归属一个主知识库；知识点之间仍通过现有 `knowledge_relation` 构建关系图。这不是要求把知识关系限制成严格树：知识点可以有多个相关关系，但其主归属清晰。

用户选择多个知识库练习时，题目通过现有 `question_knowledge` → `knowledge` → `knowledge_base` 的关联筛选，不必在 `question` 表冗余存一份知识库 ID。

## 3. V1.0 的范围

本次先做“顶层领域分类”，不要同时实现任意深度的分类树、跨库自动归属、知识图谱可视化或复杂权限系统。

知识库初始数据建议：

- Android
- Java
- 分布式系统
- C 语言
- 未分类

用稳定的 `code` 标识，如 `android`、`java`、`distributed_systems`、`c_language`、`uncategorized`。初始化必须幂等，不得重复插入。管理员以后可以新建领域。

旧知识和旧导入任务不要由 LLM 在数据库迁移期间自动分类。迁移时统一放到“未分类”，然后由管理员通过知识点编辑或批量调整重新归类，避免自动归类错误污染正式数据。

## 4. 修改规模评估

这是一次可控的增量改造，而不是大重构。预计涉及：

- 数据库：增加 `knowledge_base`，给 `knowledge` 和 `knowledge_import_task` 增加外键归属字段；执行安全迁移并回填旧数据。
- 后端：增加知识库 CRUD/查询 API；知识点列表按库过滤；导入任务接收知识库 ID；去重和向量搜索按库限定；向量元数据补充知识库 ID。
- 管理后台：增加知识库列表/管理与按库查看知识点；新建导入任务时选择目标知识库；知识点新建/编辑展示所属库。
- 测试：迁移、现有接口回归、知识库作用域去重、向量索引回填、导入任务参数测试。

不需要：替换 FastAPI、SQLAlchemy、Alembic、MySQL、LangGraph 或现有 Vector DB；不需要引入 Redis、Celery、RabbitMQ；暂时不实现用户端选择知识库的 UI。

## 5. 必须按这个顺序执行

### 阶段 A：DSH 后端实现知识库基础能力

执行文档：`01_KnowledgeBase_V1.0_后端开发指导文档_DSH.md`

只修改 `backend/`。完成数据库迁移、后端 API、导入任务上下文、知识点过滤和向量索引作用域。这个阶段先不把 `KnowledgeRelationAgent` 接进正式导入流程。

### 阶段 B：Claude Code 改管理员前端

执行文档：`02_KnowledgeBase_V1.0_管理后台改造指导文档_ClaudeCode.md`

只修改 `admin-web/`。使用阶段 A 实际交付的 API 契约；如后端接口细节与文档建议略有不同，应先让 DSH/Claude Code 对齐契约，不允许 Claude Code 自行新增后端 API 或修改 `backend/`。

### 阶段 C：DSH 正式集成 KnowledgeRelationAgent

执行文档：`03_KnowledgeRelationAgent_ImportTask正式集成_V1.0_DSH.md`

必须等 A 完成，且 B 的导入选择知识库、筛选知识点等功能已联调通过后再执行。只修改 `backend/`。所有关系候选检索都要接收当前任务的 `knowledge_base_id`。

## 6. 当前版本的归属与检索规则

1. 每个知识点只拥有一个 `knowledge_base_id`；V1.0 暂不做“同一个知识点同时属于多个库”。
2. 新导入任务由管理员显式选择一个目标知识库。为兼容旧 API/脚本，如果历史调用没有传 ID，后端可以落到“未分类”，但后台的新建导入表单必须要求选择。
3. 数据库去重范围默认只包含同一个知识库内可用的知识点。
4. RelationAgent 候选范围默认只包含同一个知识库内可用的知识点。
5. 向量搜索要优先使用 `knowledge_base_id` 元数据过滤。如果当前 Vector DB 不支持元数据过滤，须由 DSH 检查实际能力并采用现有架构中的最小安全适配；不能把其他知识库的结果不加区分地交给 Agent。
6. Vector DB 是检索索引，MySQL 是正式事实来源。不能因向量查询失败而将所有候选误判成 `NEW` 或 `NO_RELATION`。
7. 用户日后选择多个知识库出题时，以多选知识库 ID 为筛选条件，并通过题目关联知识点表过滤；当前只准备后端数据结构，不要求这次实现用户练习端。

## 7. 每个阶段的交付

每个阶段都必须给出：

- 修改文件清单及修改理由。
- Alembic 迁移方式、旧数据回填结果、回滚注意事项。
- 实际运行的测试命令和真实结果。
- 未执行或因环境未能执行的测试，明确标记，不得声称通过。
- 至少一条真实 API 验证流程。
- 不做范围外重构，不修改另一个工具负责的目录。

建议现在先让 DSH 执行阶段 A；不要同时让两个 CLI 修改同一个后端项目。
