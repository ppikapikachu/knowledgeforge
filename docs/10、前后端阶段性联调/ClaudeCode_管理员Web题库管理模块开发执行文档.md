## 0. 执行原则（必须先读）

### 0.1 本次开发目标

本次不是重新设计整个管理系统，也不是开发普通用户答题端。目标是让管理员能够在浏览器中完成以下闭环：

**管理员登录 → 选择题库和知识点 → 创建 AI 出题任务 → 查看任务执行情况 → 审核 AI 生成题目 → 发布题目 → 在正式题目列表中管理题目。**

### 0.2 代码修改边界

1. **只允许修改 `admin-web/` 目录内的前端代码。**
2. 不允许修改 `backend/`、数据库迁移、Python Agent、后端接口或后端文档。
3. 不允许修改 Flutter 用户端。
4. 不允许为了让页面跑通而新增 Mock API、假数据、假统计数字或本地模拟任务状态。
5. 不允许擅自改写已经存在的登录、权限、路由、Axios/fetch 封装、UI 组件库和项目设计规范。先检查并复用。
6. 如果发现后端契约缺字段、枚举不明确或接口无法完成某项交互，记录为阻塞项，输出给项目负责人，不得在前端猜字段或通过假数据掩盖。
7. 除非确实阻塞本次闭环，不要引入新依赖。优先复用项目已有组件和工具。

# 1. 产品定位与成熟产品参考

本模块定位为**管理员题目生产与质量管理工作台**，不是普通用户考试页面。

参考 Moodle Question bank 和 Canvas Question Banks / Item Banks 的成熟设计思路，但只吸收适合当前阶段的部分：

| 成熟产品中的做法 | 本项目采用方式 | 本次范围 |
|---|---|---|
| Moodle 将题目集中放在题库中管理，提供分类、筛选、预览、编辑等操作 | 本项目以题库为筛选主维度，题目可按知识点、类型、难度、状态检索 | 实现 |
| Moodle 区分题目状态，并在题目管理中提供预览、编辑、复制、版本历史等操作 | 本项目先实现待审核、已发布、已驳回、已下架状态；提供题目预览和编辑 | 实现状态、预览、编辑；暂不做复制和版本历史 |
| Moodle 提供关键词、类别、题型、状态等筛选，适合管理较大的题库 | 本项目使用后端已有筛选条件和服务端分页 | 实现 API 已支持的条件 |
| Canvas 将 Question Bank 作为可复用题目仓库，题目可以被多个测验使用 | 本项目的题库是后续用户组卷时的题目来源，发布状态决定是否可用于组卷 | 本次只管理题库归属，不开发组卷 |
| Canvas 支持查看题目详情、移动/复制题目到其他题库 | 当前后端没有对应的移动/复制 API | 暂不实现 |

设计原则：

1. 页面采用后台工作台风格：清楚的页面标题、筛选区域、数据列表、状态标签、明确的主要操作。
2. 信息密度适中，题目列表不直接塞入全部题干、选项和解析；通过详情页/抽屉查看完整内容。
3. 对“生成任务”和“题目审核”两个不同对象分开管理，不把任务状态误当成题目状态。
4. 所有重要状态必须有文字，不只靠颜色表达。
5. 操作完成后更新服务端数据；不得只修改前端本地状态假装保存成功。
6. AI 生成内容默认不直接视为正式可用题目，必须经过管理员审核并发布。

参考资料链接见本文末尾“成熟产品参考”。

# 3. API 接入总规范

## 3.1 Base URL 与认证

后端 API 文档当前给出的本地 Base URL：

```text
http://localhost:8000/api/v1
```

生产/测试环境必须走项目现有环境变量配置，不允许在业务组件中散落硬编码 URL。

认证方式：管理员登录后获得 Bearer Token。复用现有登录状态、Token 存储和请求拦截器，发送业务请求时附加：

```http
Authorization: Bearer <token>
```

不要另起一套 Token 管理，不要把 Token 写进页面组件或提交到代码仓库。

## 3.2 统一响应结构

后端约定：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

但必须核查实际 `ApiResponse` 封装和异常响应格式。优先复用项目已有的请求封装：

- 统一处理 HTTP 状态码和业务 `code`。
- 正确解析 `data`，不要每个页面重复拆包。
- 401/认证失效时按现有路由守卫流程处理。
- 表单校验错误、业务错误和网络错误要分别显示。
- 后端返回的 `message` 可用于错误提示，但不要把堆栈、SQL 或敏感服务信息直接展示给普通管理员。

## 3.3 API 路径

以下路径相对于 `/api/v1`：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/auth/login` | 管理员登录（复用现有登录） |
| GET | `/question-banks` | 题库列表 |
| GET | `/question-banks/{id}` | 题库详情 |
| GET | `/knowledge` | 知识点列表 |
| POST | `/question-generation/tasks` | 创建生成任务 |
| GET | `/question-generation/tasks` | 生成任务列表 |
| GET | `/question-generation/tasks/{id}` | 生成任务详情 |
| GET | `/questions` | 题目列表 |
| GET | `/questions/{id}` | 题目详情 |
| PUT | `/questions/{id}` | 编辑题目 |
| DELETE | `/questions/{id}` | 下架题目（软删除） |
| POST | `/question-generation/questions/{id}/review` | 发布或驳回题目 |

**请求参数和响应字段不能仅根据路径名推断。** 编码前从实际 OpenAPI 和后端 Schema 核对 query 参数、分页字段、ID 类型、响应层级、题目选项字段、答案字段、任务进度字段及错误字段。

### 3.4 枚举必须从后端核对

后端 API 文档确认的状态枚举：

**QuestionStatus**

- `pending_review`：待审核
- `published`：已发布，可组卷
- `rejected`：已驳回
- `disabled`：已下架

**TaskStatus**

- `pending`：待执行
- `running`：执行中
- `success`：全部成功
- `partial_success`：部分成功
- `failed`：失败

生成任务请求样例中确认：

- `question_type` 示例值：`SINGLE_CHOICE`
- `difficulty` 示例值：`2`
- `count` 示例值：`5`

这些样例**不代表完整枚举列表或难度映射**。必须从后端 Enum/Schema 确认所有题型和难度值，以及每个值对应的中文名称。禁止自行猜测 `MULTIPLE_CHOICE`、`TRUE_FALSE` 或难度 1/2/3 的含义。若后端没有明确暴露完整枚举，记录阻塞项，不能通过前端硬编码猜测上线。

## 3.5 建立 API 层与页面解耦

按项目已有目录约定组织代码。若当前项目没有类似分层，建议建立：

```text
src/

│   ├── questionBank.ts
│   ├── knowledge.ts
│   ├── questionGeneration.ts

```

这只是建议结构，应优先服从项目已有架构，不要为了匹配示例而大幅搬迁现有代码。

要求：

- 业务页面不得直接散落 `axios.get(...)`。
- API 调用统一放在 API service 层。

# 4. 页面一：AI 生成题目

## 4.1 页面目标

管理员选择一个目标题库、一个知识点、一种题型、一个难度和生成数量，提交后端后台任务。当前后端一次请求只接受一个知识点、一种题型和一个难度，第一版 UI 必须忠实反映这一能力。

**不要把页面做成多知识点、多题型、多难度的组合生成器。** 目前没有批量组合请求契约，不能在前端伪装成一个任务或偷偷拆出很多请求。

## 4.2 页面布局

建议分为：

1. 页面标题和简短说明。
2. 出题参数卡片。
3. 提交按钮和参数说明。
4. 最近生成任务入口（可选，数据必须来自任务列表 API；不要展示虚构统计）。

### 表单字段

| 字段 | 控件 | 数据来源/规则 |
|---|---|---|
| 目标题库 | 单选下拉，支持搜索 | `GET /question-banks` |
| 知识点 | 单选下拉，支持关键词搜索和分页 | `GET /knowledge` |
| 题型 | 单选下拉 | 后端完整 Enum/Schema |
| 难度 | 单选下拉 | 后端完整 Enum/Schema |
| 生成数量 | 数字输入 | 最小值、最大值以实际后端校验规则为准 |

题库和知识点数据量可能增长，必须优先使用远程搜索/服务端分页能力，不要一次性把全部知识点加载到浏览器。若现有接口支持分页，则使用服务端分页；若下拉组件支持虚拟滚动，可复用。

## 4.3 题库与知识点关系处理

当前 API 文档只明确分别提供 `GET /question-banks` 和 `GET /knowledge`，以及创建任务时分别传 `question_bank_id` 和 `knowledge_id`。就绪报告说明后端会校验题库和知识点存在，但没有明确记载存在可查询的题库—知识点映射接口。

因此：

- 不得假设选中题库后，知识点必然能按题库自动过滤。
- 先检查现有 API/Schema 是否提供明确映射或过滤参数；存在则使用。
- 若没有映射能力，使用知识点列表的已有搜索/分页能力，允许管理员分别选择，并在表单旁说明“生成题目将归入所选题库，并关联所选知识点”。
- 不得自行根据题库名称、知识库名称或字符串包含关系过滤知识点。
- 提交前做必填校验，后端负责最终合法性校验。

## 4.4 提交请求

当前后端文档示例：

```json
{
  "knowledge_id": 1,
  "question_bank_id": 1,
  "question_type": "SINGLE_CHOICE",
  "difficulty": 2,
  "count": 5
}
```

必须以实际 Schema 为准，保持字段类型与枚举值一致。

## 4.5 提交交互

1. 提交前显示参数摘要：目标题库、知识点、题型、难度、数量。
2. 点击“开始生成”后立即禁用提交按钮并显示 loading，防止重复点击。
3. 接口成功返回 `task_id` 后提示“任务已创建”，跳转至任务详情页。
4. 如果发生网络超时且前端无法确定服务器是否已创建任务，不要自动重试 POST。提示管理员先去任务列表检查是否已创建，避免重复创建任务。
5. 若业务校验失败，展示后端明确错误信息，并保留用户已填写的表单内容。
6. 页面不得等待模型生成完毕；创建接口应快速返回，生成过程在任务页面观察。

## 4.6 第一版明确不显示的选项

后端报告明确指出 AI 解析自动生成尚未实现，因此本页面**不要显示“同时生成简易解析”复选框**，也不要让管理员误以为勾选后会起效。

后续解析生成能力和任务接口完成后，再单独增加该设置。

# 5. 页面二：生成任务列表与详情

## 5.1 任务列表

使用 `GET /question-generation/tasks`。

页面目标：快速找到任务，识别正在执行、已完成、部分成功和失败任务。

推荐列表列：

- 任务 ID（以 API 实际返回字段为准）
- 目标题库
- 知识点
- 题型
- 难度
- 计划生成数量
- 成功/失败数量（如果 API 提供）
- 任务状态
- 创建时间/完成时间（如果 API 提供）
- 操作：查看详情

不要展示后端未返回的字段。尤其不能用当前时间伪造创建时间或根据任务状态猜测数量。

筛选：

- 任务状态：全部、pending、running、success、partial_success、failed。
- 服务端分页；使用 API 实际支持的参数名。

## 5.2 任务详情

使用 `GET /question-generation/tasks/{id}`。

详情至少围绕后端明确承诺的数据组织：

1. 任务基本参数。
2. 任务状态。
3. 进度/计划数/已生成数（仅在响应包含时展示）。
4. 关联生成题目列表。
5. 错误摘要。

任务详情 API 在 DSH 报告中说明会返回“参数、进度、关联题目列表、错误摘要”，但具体字段名称和结构需要根据真实 Schema 读取。必须在 API adapter 层适配，不得发明 `progress_percent` 或 `success_count` 等字段。

### 任务状态文案

| API 状态 | 中文状态 | UI 行为 |
|---|---|---|
| `pending` | 等待执行 | 展示等待状态；可手动刷新 |
| `running` | 执行中 | 展示运行状态；详情页短间隔轮询 |
| `success` | 全部成功 | 停止轮询；展示结果题目 |
| `partial_success` | 部分成功 | 停止轮询；同时展示成功题目和失败信息 |
| `failed` | 生成失败 | 停止轮询；突出显示错误摘要 |

不能将 `partial_success` 简化成普通“成功”，必须让管理员知道有部分题目未生成。

## 5.3 详情轮询

- 仅对 `pending`、`running` 任务轮询。
- 建议间隔约 3 秒，允许根据项目请求频率策略调整。
- 离开任务详情路由时清理定时器。
- 页面卸载、任务进入终态、请求失败持续达到合理上限时停止或退避轮询，提供手动刷新入口。
- 不允许多个组件同时对同一任务重复轮询。
- 浏览器刷新或复制详情 URL 后，应通过 URL 中的 taskId 重新请求详情。
- 不允许仅靠前端内存状态记录任务进度。

### 服务重启限制

DSH 报告说明：后端进程重启后，遗留的 `running` 任务目前不会自动恢复，也不会自动标记为失败。

前端必须：

- 如实显示 API 返回的 `running` 状态。
- 不允许在前端自行将它改成 `failed` 或 `success`。
- 若任务持续很久无进度且 API 未提供心跳/更新时间，只能显示“任务仍处于执行中，当前服务尚未提供自动恢复状态”，提供刷新和返回任务列表入口；不能宣称任务已恢复或一定卡死。
- 不提供“自动重试”按钮，因为后端目前没有任务重试契约。

## 5.4 任务结果到审核

任务详情中对成功生成的题目提供“查看并审核”入口。

- 如果任务详情返回关联题目 ID，可跳转到对应题目详情或待审核页面。
- 如果返回完整题目数据但无独立 ID，不能自行构造 ID；先根据响应字段确认后端如何关联题目。
- 如果任务部分成功，成功题目仍应可进入审核，失败项展示错误摘要。
- 当前题目列表 API 文档未说明支持 `generation_task_id` 筛选，不得擅自添加此 query 参数。

# 6. 页面三：题目审核

## 6.1 目标

AI 生成题目默认进入 `pending_review`，管理员审核通过后成为 `published`，驳回则成为 `rejected`。只有已发布题目进入正式可组卷题库。

题目生命周期：

```text
AI 生成
  ↓
pending_review（待审核）
  ├── 管理员发布 → published（已发布，可组卷）
  └── 管理员驳回 → rejected（已驳回）

published（已发布）
  └── 管理员下架 → disabled（已下架）
```

以 API 状态为准。审核列表默认请求 `GET /questions` 并传入实际支持的 `status=pending_review` 参数。

## 6.2 待审核列表

建议筛选：

- 题库
- 知识点
- 题型
- 难度
- 题目关键词

以上筛选以 `GET /questions` 实际支持的字段为准。

推荐列：

- 题目摘要/题干首行
- 题库
- 关联知识点
- 题型
- 难度
- 状态
- 操作：审核

列表只展示摘要，不展开完整选项、答案和长解析，以保证可扫描性。

采用服务端分页。切换筛选项后重置到第一页。搜索建议做 300–500ms 防抖，避免每敲一个字发送一次请求。

空状态需区分：

- 当前无待审核题目：提示“暂无待审核题目”。
- 筛选条件没有结果：提示调整筛选条件。
- 请求失败：显示错误及重试，不要将错误渲染成空列表。

## 6.3 题目审核详情

调用 `GET /questions/{id}` 获取完整详情。

建议使用两栏或分区布局：

**左侧/主要区域：题目内容预览**

- 题干
- 题型
- 难度
- 选项（如该题型有选项）
- 正确答案
- 简易解析（可能为空）
- 关联题库
- 关联知识点

**右侧/辅助区域：审核信息与操作**

- 当前审核状态
- 题目基础信息
- 编辑题目
- 发布
- 驳回

复用同一个 `QuestionPreview`，让审核预览尽量接近未来用户实际看到的题目样式，但管理员审核页必须明确展示正确答案和解析。

### 题目类型兼容

- 按后端返回的真实题型渲染。
- 选择题显示选项及正确选项标识。
- 判断题按后端存储结构展示判断选项/答案。
- 简答题展示参考答案。
- 不要只支持单选题而在其他题型静默丢字段。
- 如果遇到前端尚未支持的题型，应展示可读的原始信息/不支持提示，并在交付报告记录，不能错误展示成单选题。

## 6.4 编辑题目与历史答题保护

使用 `PUT /questions/{id}`。

后端保护规则：

| 题目是否已有答题记录 | 允许修改 |
|---|---|
| 无答题记录 | 题干、选项、答案、解析、难度 |
| 有答题记录 | 仅解析、难度、元数据 |

后端负责最终保护，前端必须处理其业务错误。

如果详情 API 返回 `has_answer_records`、可编辑字段列表或类似权限标记，按该字段控制表单。如果没有该字段：

- 不要仅凭题目状态、题目 ID 或本地缓存推断有没有答题记录。
- 可以正常展示编辑入口。
- 提交后如果后端拒绝核心内容修改，显示后端业务提示，保留用户编辑内容，并提示只能修改解析、难度或元数据。
- 不允许通过拆分多个请求绕开后端保护。

### 解析编辑

当前后端已有 `explanation` 字段和手动编辑标记规则：编辑解析会自动设置 `explanation_source=manual`。

本次支持管理员手动编辑解析；保存时按真实 PUT Schema 提交。保存成功后重新获取详情，确保页面展示服务端持久化内容。

解析可为空。不要把空解析自动补成假文案。

本次暂不显示 AI 解析生成按钮，因为后端尚未实现 AI 解析生成任务。

## 6.5 发布

调用：

```http
POST /question-generation/questions/{id}/review
Content-Type: application/json
```

请求示例：

```json
{
  "action": "publish",
  "reason": ""
}
```

具体是否允许省略 `reason` 以实际 Schema 为准。

发布交互：

1. 如果管理员已经编辑题目，先保存编辑。
2. 保存成功后再提交发布。
3. 发布按钮显示 loading，避免重复提交。
4. 发布成功后重新获取题目状态，确认已经成为 `published`。
5. 从待审核列表移除该题，更新列表总数。
6. 提供“查看正式题目”跳转。

## 6.6 驳回

调用同一接口：

```json
{
  "action": "reject",
  "reason": "内容不准确"
}
```

交互要求：

- 点击驳回打开确认弹窗。
- 要求管理员填写驳回原因（建议至少 2 个字符；长度上限以 Schema 为准）。
- 清楚提示驳回后该题不会进入正式可组卷题库。
- 成功后刷新列表并从待审核队列移除。
- 后端若返回错误，应保留驳回原因文本，便于修正重试。

## 6.7 审核操作边界

- 第一版不做批量发布/批量驳回，因为当前 API 没有批量接口。
- 不允许将题目状态直接在前端改为 `published`。
- 只有审核接口成功后，才能显示发布成功。
- 已 `published` 或 `rejected` 的题目不应继续显示“发布/驳回”按钮，按钮显示逻辑以真实状态为准。

# 7. 页面四：正式题目列表与详情

## 7.1 页面目标

统一查看各状态的题目，并对已发布题目进行常规维护。

调用 `GET /questions`。

建议筛选：

- 题库
- 知识点
- 题型
- 难度
- 状态：全部、待审核、已发布、已驳回、已下架
- 关键词

如果页面默认只想管理正式题目，可将初始状态设为 `published`，但必须让管理员能切换到其他状态。

## 7.2 列表字段

建议列：

- 题目摘要
- 题库
- 知识点
- 题型
- 难度
- 状态
- 解析状态/解析是否存在（仅当接口实际返回）
- 最后更新时间（仅当接口实际返回）
- 操作：查看、编辑；已发布题目可下架

不展示当前 API 没有提供的累计答题人数、准确率、使用次数、评论数、创建人等信息。不要生成 0、-- 或虚构统计作为占位指标。

## 7.3 题目详情

调用 `GET /questions/{id}`。

至少提供：

- 完整题目预览。
- 题库和知识点归属。
- 题型、难度和状态。
- 正确答案和解析。
- 编辑入口。
- 下架入口（仅适用状态）。

## 7.4 编辑规则

复用审核页面的题目编辑表单。不要为审核和列表分别写两套字段逻辑。

保存通过 `PUT /questions/{id}`。后端可能因为历史答题记录而拒绝修改题干/选项/答案，前端需要准确呈现业务错误。

若题目已被用户答过，修改解析时不应改变题目答案。编辑成功后重新 GET 详情，确认后端返回的数据。

## 7.5 下架

当前 `DELETE /questions/{id}` 的业务语义是软删除/下架，不是物理删除。

前端按钮文案必须使用：**下架题目**，不能简单写“删除”。

点击后确认弹窗应说明：

“下架后，该题目将不再作为正常可组卷题目使用。系统保留历史记录，是否继续？”

确认后调用 DELETE，成功后刷新列表，并将当前题目显示为 `disabled`（以服务端实际返回为准）。

已下架题目不显示重复下架操作。若没有恢复接口，不要提供“恢复上架”按钮。

# 8. 核心业务规则与前端状态管理

## 8.1 两套状态不得混淆

**任务状态**代表某次 AI 生成任务的执行结果；**题目状态**代表单道题目是否经过审核、是否可用。

一个任务可能 `success`，但其中的题目仍然是 `pending_review`；任务部分成功时，成功生成的题目也仍然需要逐道审核。

不能因为 TaskStatus 为 `success` 就认为题目已发布。

## 8.2 页面通用状态

每个异步页面至少有：

- 首次加载 loading。
- 正常数据状态。
- 空状态。
- 请求错误状态与重试入口。
- 提交/保存 loading。
- 操作成功或失败反馈。

避免页面在请求失败时显示空列表，也避免多个重复 toast。

## 8.3 列表筛选和分页

- 所有支持分页的列表优先使用服务端分页。
- 页码、pageSize 参数按后端实际命名；不能默认认为一定是 `page`、`page_size`。
- 筛选条件变更后重置页码。
- 翻页后保留筛选条件。
- 从详情返回列表时，尽量恢复原查询条件和页码；可使用 URL query 或项目现有列表状态方案。
- 搜索框防抖 300–500ms。
- 对下拉选项使用分页/远程搜索，避免全量拉取超大知识点集合。

## 8.4 网络和重复操作

- 创建任务、发布、驳回、编辑、下架都必须有请求中的 loading 和防重复提交。
- GET 请求可根据项目策略重试；创建任务 POST 不可在网络超时后自动重试。
- 请求失败后保留表单内容。
- 操作成功后以服务端重新拉取的数据为准。

## 8.5 安全

- 依赖后台登录和服务端权限校验，前端路由守卫不能替代后端授权。
- 不将 Token 暴露在 URL、日志或错误提示中。
- 如果题干/解析以 Markdown 或富文本展示，使用项目已有且经过安全处理的渲染方式；防止不安全 HTML 注入。
- 题目内容可能包含代码、换行、符号、中文和 Markdown 格式，预览不能随意去掉空格、换行或转义字符。

# 10. UI/UX 具体要求

## 10.1 视觉方向

- 延续现有管理后台的品牌色、主题和布局，不要另起一套风格。
- 桌面端优先，主要适配 1280px 及以上工作区；较窄窗口下表格允许横向滚动或合理隐藏次要列，不得布局溢出。
- 页面保持简洁、专业、易扫描，避免过多渐变、玻璃拟态、装饰性大图、夸张动画。
- 主要按钮突出一个主操作，危险操作使用明确的危险样式并二次确认。
- 状态使用统一 Tag/Badge 组件，颜色和文字一致。
- 表格行高、筛选间距、表单标签、空状态、弹窗行为遵循现有 Design System。

## 10.2 交互细节

- 题库和知识点下拉支持远程搜索。
- 长题干在列表截断显示，详情完整展示。
- 题目详情支持代码段/换行可读展示。
- 正确答案在审核详情中明显但不过度装饰。
- 发布、驳回、下架等不可逆或影响业务的操作都要有确认反馈。
- 操作结束后给出明确结果，并更新相关列表。
- 长任务页面应支持刷新后继续查看。
- 避免把任务列表、题目审核、题目正式列表混在同一页签里。

## 10.3 可访问性

- 所有表单控件有标签。
- 不只用颜色表达状态。
- 键盘可完成表单主要操作。
- 对话框打开后焦点进入弹窗，关闭后返回触发按钮（复用现有组件能力）。
- 错误提示明确指出哪个字段需要修正。

# 11. 联调与验收测试

必须连接真实后端进行端到端验证。本次运行环境允许使用真实 API，不允许在应用运行时切换到 Mock。

## 11.1 基础联调

1. 启动后端。
2. 按项目现有方式启动 `admin-web`。
3. 使用真实管理员账号登录。
4. 验证 Bearer Token 自动附加。
5. 验证未登录访问受保护页面时能正确跳回登录流程。
6. 验证 API 响应统一拆包和异常提示。

不要把 DSH 报告里的 `admin/admin123` 当成生产凭据硬编码；仅在本地测试环境确认该账号可用时用于冒烟测试。

## 11.2 AI 生成题目验收

- 题库下拉真实加载。
- 知识点下拉真实加载并可搜索/分页（按接口能力）。
- 题型、难度选项与后端枚举一致。
- 空值、非法数量、未选题库/知识点时前端阻止提交。
- 正常提交后得到真实 task_id。
- 连续快速点击不会创建多条重复任务。
- 网络超时后不自动重发 POST，并提示先检查任务列表。

## 11.3 生成任务验收

逐项验证 `pending`、`running`、`success`、`partial_success`、`failed` 五种状态（若环境里没有真实任务覆盖全部状态，可用后端已有测试数据/专门测试环境验证；不得在正式前端中写模拟状态）。

- 任务列表筛选和分页正常。
- 点击任务进入详情。
- `pending/running` 任务按预期轮询。
- 页面离开后轮询停止。
- 刷新任务详情 URL 可重新读取任务。
- 成功任务可定位生成题目。
- 部分成功展示成功结果及失败摘要。
- 失败任务展示错误摘要。
- 任务状态为成功不应导致题目自动显示为已发布。

## 11.4 题目审核验收

- 待审核列表仅查询 `pending_review`。
- 筛选和服务端分页正常。
- 题目详情显示题干、选项、答案、解析、题库和知识点。
- 至少测试当前系统实际支持的每一种题型。
- 可编辑未有答题记录的题目。
- 已有答题记录的题目尝试修改题干/选项/答案时，后端拒绝后前端能清楚提示。
- 可手动编辑解析，保存后重新 GET 详情确认。
- 发布成功后题目从待审核列表消失，并在 `published` 列表中可查到。
- 驳回必须填写原因，成功后从待审核列表移除。

## 11.5 正式题目列表验收

- 题库、知识点、题型、难度、状态、关键词筛选按 API 能力可用。
- 服务端分页正常。
- 题目详情可查看。
- 有答题记录题目的核心字段编辑保护正常呈现。
- 下架操作有明确确认，调用 DELETE 后状态更新为 `disabled`。
- 下架按钮不被误称为物理删除。

## 11.6 通用验收

- 刷新页面无白屏。
- 无未捕获 Promise 错误。
- 无控制台严重错误。
- 无重复轮询/定时器泄漏。
- 无请求参数名或字段名猜测导致的 API 失败。
- 不存在运行时 Mock 数据或硬编码虚构统计。
- 页面在 1280px 桌面窗口正常显示。

# 14. 当前后端契约摘要（以实际代码再次核对）

后端 API 文档位置：

`backend/docs/API_ADMIN_QUESTION_MANAGEMENT.md`

联调就绪报告位置：

`backend/docs/ADMIN_WEB_API_READINESS_REPORT.md`

基础信息：

- Base URL：`http://localhost:8000/api/v1`
- 认证：Bearer Token
- 响应：`ApiResponse[code, message, data]`

关键调用顺序：

```text
1. POST /auth/login
2. GET /question-banks
3. GET /knowledge
4. POST /question-generation/tasks
5. GET /question-generation/tasks/{id}
6. GET /questions?status=pending_review
7. GET /questions/{id}
8. PUT /questions/{id}
9. POST /question-generation/questions/{id}/review
10. GET /questions?status=published
11. DELETE /questions/{id}  # 软删除/下架，不是物理删除
```

任务创建示例：

```json
{
  "knowledge_id": 1,
  "question_bank_id": 1,
  "question_type": "SINGLE_CHOICE",
  "difficulty": 2,
  "count": 5
}
```

任务创建响应示例：

```json
{
  "code": 0,
  "data": {
    "task_id": 1,
    "status": "pending",
    "message": "任务已创建，后台执行中"
  }
}
```

审核请求示例：

```json
{
  "action": "publish",
  "reason": ""
}
```

或：

```json
{
  "action": "reject",
  "reason": "内容不准确"
}
```

重要后端限制：

- 已有答题记录的题目不能修改题干、选项和答案；可修改解析、难度和元数据。
- 手动修改解析后后端标记 `explanation_source=manual`。
- 进程重启后遗留 `running` 任务暂不自动恢复。
- AI 解析自动生成尚未实现。

# 15. 成熟产品参考资料

以下资料用于参考成熟题库产品的管理方式，不表示本项目需要一次性照搬全部功能：

1. **Moodle 5.2 – Question banks**  
   https://docs.moodle.org/502/en/Question_banks  
   参考点：题库是集中创建、预览和编辑题目的独立空间；题目可按分类组织；筛选包含分类、题型、状态、关键词等；题目管理可展示状态、版本、创建者、评论、使用情况、最近使用时间和“需要检查”等质量信息。本文只把适合当前 API 的筛选、预览、状态管理纳入第一版，版本/使用统计/同伴评论等待后端具备能力后再做。

2. **Canvas Admin Guide – Manage Question Banks**  
   https://community.instructure.com/en/kb/articles/661566-how-do-i-create-or-manage-question-banks-in-an-account  
   参考点：从题库列表进入题库详情，在题库内管理题目，并提供题目详情查看。这支持本项目将题库管理和题目管理组织成清晰的列表—详情关系。

3. **Canvas Instructor Guide – Create a quiz by finding questions in a question bank**  
   https://community.instructure.com/en/kb/articles/660999-how-do-i-create-a-quiz-by-finding-questions-in-a-question-bank  
   参考点：题库中的题目被复用到测验/试卷。本项目的正式题库应该只容纳已审核发布、可被后续组卷使用的题目；本次不开发组卷页面。

4. **Canvas Instructor Guide – Move/copy a question between question banks**  
   https://community.instructure.com/en/kb/articles/661020-how-do-i-move-copy-a-question-from-one-question-bank-to-another  
   参考点：成熟题库会区分移动和复制语义，并说明其对已有测验的影响。本项目当前没有移动/复制 API，所以本次不开发该操作，未来实现时必须明确复制和移动的历史数据语义。
