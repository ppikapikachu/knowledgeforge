# DSH 执行文档：管理员 Web 联调前的后端接口检查与补齐

## 0. 任务目标

当前后端已经完成题目生成、题目审核、答题记录和评论等基础模块。本阶段**不重新开发 QuestionGenerateAgent，也不做大规模重构**，目标是让现有后端具备管理员 Web 可以真实操作、真实联调的题库管理 API。

本阶段完成后，管理员应该能够通过接口完整走通：

> 查询题库和知识点 → 创建出题任务 → 查看任务列表和详情/进度 → 查看生成的题目 → 编辑题目（至少支持编辑解析）→ 审核发布或驳回 → 在正式题目列表中查询到该题。

前端由另一个工具/会话负责，本任务只修改 `backend/`。

## 4. 阶段 B：生成任务 API 可运营化

### 4.1 创建任务

现有接口：

`POST /api/v1/question-generation/tasks`

先确认它是否已经支持以下能力；支持的字段必须沿用实际 Schema，不能随意重命名：

- 目标题库；
- 使用 `QuestionDecisionAgent` 生成的分配计划，或生成计划所需的用户参数；
- 目标题量；
- 题型范围；
- 难度分布；
- 指定知识点或允许系统按所选题库选择知识点；
- 当前阶段不传递/不展示尚未实现的 `generate_explanation` 自动解析生成功能。

接口行为要求：

1. 完成参数校验和权限校验后，创建持久化任务记录。
2. 尽快返回任务 ID 和初始状态，不让 HTTP 请求等待整个 LLM 生成流程。
3. 后台执行过程应更新任务状态和计数。
4. 同一任务不能被重复启动多次。
5. 任务创建失败时返回明确错误，不能留下无法处理的半成品任务。

创建接口的最终请求/响应结构以项目实际 Schema 为基础，并补入 API 文档。

### 4.2 生成任务列表

现有接口：

`GET /api/v1/question-generation/tasks`

必须支持或明确说明：

- 分页：`page`、`page_size` 或项目现有统一分页方式；
- 状态筛选；
- 题库筛选（如果任务保存了题库 ID）；
- 创建时间倒序；
- 返回任务 ID、任务名称/摘要、题库、请求题量、已生成/已保存数量、失败数量、状态、创建时间、开始时间、结束时间。

不要返回模型的内部推理内容、完整 Prompt、密钥、供应商敏感报错堆栈。

### 4.3 生成任务详情（重点检查）

如果不存在，新增：

`GET /api/v1/question-generation/tasks/{task_id}`

建议返回：

- 任务基础信息：任务 ID、创建人、题库 ID、创建时间；
- 任务参数：题量、题型、难度、知识点分配摘要；
- 执行信息：状态、进度、请求数量、生成数量、成功保存数量、重复数量、校验失败数量、失败数量；
- 时间信息：开始时间、结束时间、最近更新时间；
- 结果列表：关联题目 ID、题目类型、难度、知识点、保存状态；
- 失败摘要：失败阶段和可读错误原因。

任务状态必须沿用项目已有状态枚举。如果当前状态没有表达部分成功的能力，可评估补充 `partial_success`；不要让同一个状态在不同 API 中含义不一致。

进度计算必须有明确定义。例如：

`progress = 已处理的计划项数量 / 总计划项数量 * 100`

不能简单将 LLM 请求发出就当成题目生成完成。无法精确获得百分比时，应返回状态和计数，不要伪造精确进度。

### 4.4 任务结果明细的持久化

检查现有模型是否能持久保存每个计划项/每道题的执行结果。

如果当前只能保存总成功数和失败数，管理员无法知道哪道题成功、哪道题失败，则需要增加合理的任务明细持久化方案。优先扩展现有任务模型/结果结构；只有在确实需要逐项追踪、重试和展示时，才新增类似 `question_generation_item` 的子表。

每个明细至少能够区分：

- 待处理；
- 正在生成；
- 已保存；
- 重复而跳过；
- 校验失败；
- 生成失败。

保存成功的明细应能关联 `question_id`。失败信息保存安全、简短、可供管理员理解的摘要。不要将原始模型响应或内部思维链保存为前端可见内容。

## 5. 阶段 C：题目查询、详情和编辑 API

### 5.1 题目列表

复用现有问题查询接口；如果不支持管理需要的筛选，再补齐。

管理员 Web 至少需要：

- 分页；
- 按题库筛选；
- 按知识点筛选；
- 按题型筛选；
- 按难度筛选；
- 按状态筛选（如 `pending_review`、`published`、`rejected`、`disabled`，实际值以项目枚举为准）；
- 按题干关键词搜索；
- 按创建时间排序。

列表响应应提供展示所需摘要：题目 ID、题干摘要、题库、知识点摘要、题型、难度、审核状态、是否有解析、创建时间。

必须使用数据库分页，不要一次性把全部题目取到 Python 内存后再分页。

### 5.2 题目详情

详情接口应能返回：

- 完整题干；
- 选择题选项及其顺序；
- 正确答案；
- 解析及解析状态、来源；
- 题库归属；
- 关联知识点；
- 题型、难度、审核状态；
- 创建时间、更新时间；
- 来源生成任务 ID（如果存在）。

管理员可以看到正确答案；将来用户答题接口必须按答题阶段控制答案字段，不能复用管理员详情响应导致用户提前看到答案。

### 5.3 题目编辑

检查现有更新接口是否足够。若无，补充一个符合项目风格的管理员更新接口。

第一阶段至少允许：

- 编辑解析（包括手动添加/修改）；
- 编辑题干；
- 编辑选项及顺序；
- 编辑正确答案；
- 修改难度、知识点等允许修改的元数据。

**历史答题数据保护规则：**

1. 修改解析不影响历史判分。
2. 如果题目已有答题记录，不允许无提示地直接覆盖题干、选项或标准答案。
3. 对已被使用的题目，核心内容修改应采用“复制为新题/新版本”的安全策略；如果本项目当前没有版本表，本阶段可以先禁止核心内容直接修改，并返回明确业务错误。不要为赶页面进度而破坏历史统计。
4. 修改后必须重新校验题目结构。
5. 如果题目已发布，编辑是否需要重新审核必须有统一规则。建议核心内容变更后回到待审核状态；仅修改解析可以按项目权限规则保存，但应记录更新时间和操作者。

解析字段规则：

- `explanation` 允许为空；
- 管理员手动编辑后设置 `explanation_source=manual`（按现有枚举/字段约定）；
- 不得宣称 AI 自动解析生成功能已完成；
- 未来开发 AI 解析生成时，必须保护手动解析，不允许后台任务覆盖。

## 6. 阶段 D：题目审核接口核验

现有接口：

`POST /api/v1/question-generation/questions/{id}/review`

请核验并补齐：

- 只允许具有管理员权限的用户调用；
- 支持发布和驳回，具体请求字段以现有 Schema 为基础；
- 驳回时建议记录驳回原因；
- 已发布题目不能重复审核造成状态错乱；
- 被驳回题目不能进入正式组卷；
- 只有审核通过且状态为可用的题目才能进入正式组卷；
- 审核操作应记录操作者和时间（项目已有审计字段则复用）。

审核接口必须使用事务，避免状态更新一半、关联数据未更新的情况。

如果当前没有“恢复/下架”题目能力，本阶段可以先保证发布/驳回正确；题目下架可以复用已有题目状态更新接口，不要为了凑功能另建重复 API。

## 7. 阶段 E：认证、任务线程和可靠性检查

### 7.1 管理员认证和权限

所有管理员操作 API 必须沿用现有登录体系和依赖。不能只在前端隐藏按钮而不做后端鉴权。

至少验证：

- 未登录请求返回未认证错误；
- 普通/无权限身份不能创建出题任务、审核或编辑题目；
- 管理员可以访问允许的管理 API；
- 不能通过修改 URL 的 ID 操作不属于当前权限范围的数据。

本阶段不创建普通用户体系，也不要将用户答题/评论接口混入管理员 API。

### 7.2 Threading 后台任务

项目目前使用 Python `threading`。本阶段可以继续使用，不要求引入 Celery、Redis 或消息队列，但必须检查并处理以下问题：

1. **防止重复执行：** 同一个 `task_id` 只能有一个执行者。使用数据库状态条件更新/事务锁等项目适用方式，不能只依赖 Python 内存中的字典或锁。
2. **进程重启：** 服务启动时检查遗留的 `running` 任务。当前若没有断点续跑能力，应将其安全标记为 `failed` 或明确的 `interrupted`，写入可读原因，不能永远停留在 `running`。
3. **异常捕获：** 后台线程顶层必须捕获异常并更新任务状态、结束时间和错误摘要。
4. **数据库会话：** 后台线程必须创建独立 SQLAlchemy Session，不能直接共享请求线程的 Session。
5. **资源清理：** 任务结束时关闭 Session 和释放资源。
6. **并发约束：** 如果当前部署使用多个 Uvicorn/Gunicorn worker，必须说明内存线程方案的边界。当前开发阶段如仍采用单进程，需在文档中明确这一约束；不要声称该方案已支持多实例分布式任务执行。
7. **失败任务处理：** 不要自动重试已经部分保存题目的任务，除非确认有可靠幂等机制；避免重试后生成重复题目。

### 7.3 日志与错误

- 为每个生成任务记录 `task_id` 关联日志；
- 给管理员返回可读错误摘要；
- 完整堆栈只写服务端日志；
- 不向前端暴露 API Key、模型供应商密钥、Prompt 内部配置或数据库连接信息。
