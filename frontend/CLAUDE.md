# CLAUDE.md - 前端项目开发规范

## 一、项目基本说明

本项目是一个前端应用，采用 Vue3 技术栈。

Claude Code 在参与本项目开发时，必须优先理解现有项目结构、技术架构和代码规范，不得在不了解现有实现的情况下直接编写或重构代码。

### 基本原则

- 优先沿用项目现有技术方案。
- 优先复用已有组件、工具类、公共方法和业务逻辑。
- 不随意引入新的依赖或第三方库。
- 不随意修改项目目录结构。
- 不擅自删除已有功能。
- 不修改与当前需求无关的代码。
- 不凭空假设项目中存在某个组件、接口或工具方法。
- 所有修改以实际源码为准。

如果项目实际技术栈、依赖或配置与本文件描述不一致，应以项目实际文件为准，并在必要时指出差异。

## 二、Codebase Memory MCP 使用规范

本项目已经接入 Codebase Memory MCP，并建立代码知识图谱索引。

**Codebase Memory MCP 是本项目日常开发时优先使用的代码检索和分析工具。**

### 1. 开发前必须优先查询索引

收到开发需求后，按照以下顺序进行：

1. 确认当前项目根目录。
2. 使用 MCP 确认当前项目是否已注册。
3. 查询与当前需求相关的页面、组件、方法、接口及依赖关系。
4. 分析相关代码的调用链和影响范围。
5. 定位需要修改的源码文件。
6. 阅读相关源码，确认实际实现后再开始修改。

不要在没有进行代码关系分析的情况下直接大范围搜索或修改代码。

### 2. 优先使用图谱查询

根据具体需求，优先使用 MCP 提供的相关能力：

- 查询项目：确认当前项目及其索引状态。
- 图谱搜索：查找相关组件、类、方法和业务模块。
- 调用链追踪：分析方法、组件和模块之间的调用关系。
- 文件结构查询：了解目标文件中的代码结构。
- 代码片段查询：快速定位需要研究的代码。
- 架构查询：了解模块划分和项目整体结构。
- 索引覆盖率检查：确认索引是否完整。

具体工具名称以当前 MCP 实际提供的工具为准，不要自行编造工具名称。

### 3. 索引使用原则

- 优先使用已有索引，不要每次任务都重新建立完整索引。
- 不要反复查询已经获取过且仍然有效的信息。
- 不要为了修改一个页面而扫描整个项目。
- 索引结果用于定位和理解代码，不能代替实际源码。
- 如果索引结果与源码不一致，以实际源码为准。
- 如果索引缺失或过期，先检查覆盖率，再考虑增量更新。
- 只有在确实需要时才进行完整重新索引。
- MCP 不可用时，说明原因并使用普通代码检索方式继续工作，不要陷入重复尝试。

### 4. 修改代码前分析影响范围

修改之前需要确认：

- 目标组件有哪些引用位置。
- 目标方法有哪些调用方。
- 是否影响其他页面。
- 是否涉及公共组件。
- 是否涉及接口请求和数据结构。
- 是否涉及全局状态或路由。
- 是否存在其他依赖该功能的业务模块。

避免只修改目标文件，却遗漏关联代码。

## 三、前端开发规范

### 1. 技术栈

项目以实际 `package.json`、配置文件和源码为准。

默认沿用项目已有的：

- Vue3
- JavaScript 或 TypeScript
- 项目现有 UI 组件库
- 项目现有路由方案
- 项目现有状态管理方案
- 项目现有 HTTP 请求封装

不要擅自将 JavaScript 改为 TypeScript，也不要擅自更换现有技术方案。

### 2. 组件开发

- 遵循现有组件组织方式。
- 公共组件应具有合理的复用性。
- 不要为了复用而过度抽象。
- 组件职责尽量单一。
- 合理使用 Props、Emits 和组件事件。
- 注意组件卸载时清理事件监听、定时器等资源。
- 不要在多个页面重复实现已有的公共功能。

### 3. 页面开发

- 优先复用现有页面布局和公共组件。
- 保持项目整体 UI 风格一致。
- 页面布局应考虑不同屏幕尺寸。
- 注意加载中、空数据、错误和异常状态。
- 表单应进行必要的参数校验。
- 列表、分页和筛选逻辑应沿用项目现有实现。
- 不要随意改变已有页面的交互逻辑。

### 4. API 接口

- 所有请求优先使用项目已有的 API 封装。
- 不要在页面组件中随意创建新的 HTTP 请求实例。
- 不要擅自修改后端接口地址、请求方式和参数结构。
- 不要凭空编造接口。
- 如果接口文档或现有代码中没有相关接口，应先说明。
- 处理好请求异常、加载状态和返回数据。
- 注意接口返回值与页面实际使用的数据结构是否一致。

### 5. 状态管理

- 优先使用项目已有的状态管理方案。
- 不要在没有必要的情况下引入新的状态管理库。
- 注意全局状态和局部状态的职责划分。
- 避免不必要的重复请求和重复状态。
- 注意页面切换、刷新后的状态处理。

### 6. 代码质量

- 命名应清晰、易于理解。
- 避免重复代码。
- 避免无意义的复杂封装。
- 删除不再使用的变量、方法和导入。
- 不要遗留大量调试日志。
- 处理必要的异常情况。
- 尽可能保持代码简洁、易维护。

## 四、项目修改边界

本项目是前端项目。

### 必须遵守

1. 默认只允许修改当前前端项目范围内的文件。
2. 不允许擅自修改后端项目代码。
3. 不允许擅自修改数据库结构和后端业务逻辑。
4. 不允许为了适配前端而自行修改后端 API。
5. 如果发现前后端接口不匹配，先指出问题并给出建议，等待确认后再处理后端。
6. 不允许擅自删除或覆盖用户已有文件。
7. 不允许未经确认执行可能造成数据丢失的操作。
8. 不允许为了完成当前需求而顺手重构无关模块。

如果需求确实涉及前后端协同修改，先说明涉及的文件、原因和修改范围。

## 五、开发任务执行流程

每次收到开发需求，按照以下流程执行。

### 第一步：理解需求

- 明确本次需要实现的功能。
- 找出涉及的业务模块。
- 确认是否有现成实现可以复用。
- 有歧义的地方先询问，不要擅自决定重要业务规则。

### 第二步：查询索引

- 使用 Codebase Memory MCP 查询相关代码。
- 找到相关页面、组件、方法和 API。
- 分析调用关系和影响范围。
- 尽量缩小源码阅读范围。

### 第三步：阅读源码

- 阅读真正需要修改的文件。
- 检查相关调用方和依赖。
- 确认现有实现和代码风格。
- 不要仅凭索引结果直接修改代码。

### 第四步：制定修改方案

对于涉及多个文件或较复杂的需求，先给出简要方案：

- 需要修改哪些文件。
- 每个文件修改什么。
- 是否需要新增组件或方法。
- 是否影响其他模块。
- 是否存在潜在风险。

简单的小修改可以直接执行，不必过度输出方案。

### 第五步：实施修改

- 只修改必要文件。
- 尽可能保持现有代码结构。
- 不要覆盖用户未要求修改的功能。
- 不要擅自引入新的依赖。
- 不要顺手修改无关代码。

### 第六步：检查验证

修改完成后：

- 检查是否存在语法错误。
- 检查相关引用是否正确。
- 检查接口参数和返回值使用是否正确。
- 检查相关页面是否受到影响。
- 根据项目现有脚本执行必要的构建、类型检查或测试。
- 如果无法验证，明确说明原因，不要声称已经验证通过。

### 第七步：汇报结果

完成后简要说明：

1. 实现了什么功能。
2. 修改了哪些文件。
3. 主要修改内容。
4. 是否有新增依赖。
5. 是否完成构建或测试验证。
6. 是否存在尚未解决的问题。

## 六、Token 和开发效率优化

开发时应尽量减少无效上下文消耗。

- 优先通过 Codebase Memory MCP 获取代码定位信息。
- 只读取与当前任务相关的源码。
- 不要反复读取同一个文件的完整内容。
- 不要无目的地遍历整个项目。
- 不要重复向 MCP 查询相同的问题。
- 不要每次任务开始都重新分析整个项目。
- 不要输出冗长的思考过程和无关说明。
- 对简单需求直接执行，对复杂需求先简要规划。
- 如果已经掌握某个模块的有效上下文，可以复用，不必重复分析。

---

## 七、最终原则

**先查询索引，再定位源码；先理解现有实现，再修改代码；先控制修改范围，再完成需求验证。**

开发过程中始终以项目现有代码、实际业务逻辑和用户明确提出的需求为准。

不要为了追求代码整洁而擅自重构，不要为了实现功能而改变无关模块，不要在没有依据的情况下编造项目结构和业务规则。
